# AI 服务器环境与部署服务探测文档系统

## 1. 项目定位

一个基于扫描器和 AI 的 Linux 服务器环境探测与运维文档生成工具。

系统连接到一台陌生的 Linux 服务器后，首先获取系统环境、版本、硬件资源、磁盘分区、挂载点和主要目录情况；随后探测服务器上已经部署和运行的服务，整理服务对应的部署目录、配置、端口、日志和数据位置，最终生成一份便于查看和接管的服务器说明文档。

核心目标：

> **自动回答“这是一台什么服务器、磁盘和目录如何组织、上面部署了哪些服务、这些服务在哪里以及如何运行”。**

本项目重点是服务器环境和已部署服务的探测整理，不以还原完整业务架构或严格分析服务依赖关系为目标。

---

## 2. 探测流程

### 2.1 获取系统基础环境

进入服务器后，优先采集以下基础信息：

* Linux 发行版和版本
* Kernel 版本
* CPU 架构、型号和核心数
* 内存和 Swap
* 主机名、时区和系统运行时间
* 虚拟机、云主机或物理机特征
* 网络接口、IP、路由和 DNS
* 防火墙状态及主要规则
* 用户、用户组及关键权限信息
* 已安装软件和软件包管理器

### 2.2 获取磁盘、分区和目录情况

采集并整理：

* 磁盘设备、容量和类型
* 磁盘分区
* 文件系统类型
* 挂载点及挂载参数
* 磁盘空间和 inode 使用情况
* LVM、RAID 等存储结构
* 主要目录及空间占用
* 数据盘、日志盘、备份盘等可识别用途
* Docker Volume 和其他重要挂载目录

目录扫描应优先覆盖常见部署位置，例如：

```text
/opt/
/srv/
/var/www/
/data/
/app/
/home/
/etc/
```

系统不需要无条件遍历整个文件系统，应结合进程、服务配置、容器挂载和常见目录逐步定位，避免扫描成本过高。

### 2.3 探测已部署服务

支持探测以下部署方式和服务类型：

* systemd 服务
* 传统直接部署的应用
* 后台进程和监听端口
* Docker 容器
* Docker Compose 项目
* Nginx
* Caddy
* MySQL / PostgreSQL / Redis 等基础服务
* 常见 Web 服务
* 可识别的自定义应用

探测时不要求用户预先指定服务位置。系统应从正在运行的进程、systemd unit、监听端口、容器信息和常见配置入口逐步定位服务。

例如：

```text
/opt/app/
    |-- docker-compose.yml
    |-- .env
    `-- config/

/etc/systemd/system/
    `-- xxx.service

/etc/caddy/
    `-- Caddyfile
```

---

## 3. 定位服务相关文件和目录

对于每个已发现的服务，扫描器应尽可能确定：

* 服务名称和当前状态
* 服务部署方式
* 服务部署目录
* 进程及启动参数
* 监听地址和端口
* 配置文件
* Docker Compose 文件
* `.env` 文件位置
* systemd unit
* Nginx / Caddy 配置
* 日志目录或日志查看方式
* 数据目录
* 挂载目录和 Docker Volume
* 备份目录
* 启动脚本
* 部署脚本
* 是否设置开机自动启动

系统只需建立服务与这些直接信息之间的归属关系，例如：

```text
Service
  |-- Process
  |-- Port
  |-- Deploy Directory
  |-- Config File
  |-- Log Location
  `-- Data Directory
```

不要求建立完整的服务依赖图，也不要求严格判断服务之间的上下游业务关系。对于反向代理目标、数据库连接地址等明显出现在配置中的信息，可以作为配置观察结果记录，但不作为依赖分析的强制目标。

---

## 4. 事实记录与探测结果

探测结果不能只是命令输出或文件列表，需要整理成统一的服务器和服务清单。

每条重要结论应尽可能记录：

* 结论内容
* 信息来源
* 采集时间
* 原始证据位置
* 确定程度

结果应区分：

* **确定事实**：由系统命令、运行状态或配置文件直接确认
* **合理推断**：根据目录、进程参数或配置内容推断
* **未知信息**：当前扫描无法确认，需要人工补充

---

## 5. AI 理解与整理

将扫描器采集到的结构化事实交给 AI，由 AI：

* 归纳服务器系统和存储环境
* 识别服务类型和可能用途
* 判断服务的部署方式
* 整理服务配置、目录和运行信息
* 将分散的扫描结果合并成服务清单
* 补充便于阅读的服务说明
* 标记明显的环境或部署风险
* 区分确定事实、合理推断和未知信息

AI 不负责凭空猜测服务器状态，也不负责自动构造完整的服务依赖关系。底层扫描结果和配置证据是文档内容的事实来源。

---

## 6. 自动生成服务器文档

最终文档至少包含以下部分。

第一版必须能够生成可直接交付和编辑的 Word 文档（`.docx`）。Markdown 或 HTML 可以作为中间产物和辅助浏览格式，但 Word 文档是默认的最终报告格式。

### 6.1 服务器概览

* 操作系统和 Kernel
* CPU、内存和 Swap
* 主机名、网络和防火墙概况
* 主要用户和权限概况
* 关键软件环境

### 6.2 磁盘与目录说明

* 磁盘和分区清单
* 文件系统和挂载点
* 空间使用情况
* 主要目录及用途
* 数据、日志、备份和容器挂载位置

### 6.3 部署服务清单

每个服务尽可能包含：

* 服务名称和用途
* 当前状态
* 部署方式
* 部署路径
* 配置文件
* 数据目录
* 日志位置和查看方式
* 进程及监听端口
* 容器、镜像和挂载信息
* 启动、停止和重启方式
* 是否开机自动启动
* 已发现的部署或启动脚本
* 已确认信息和待人工确认事项

对于无法从服务器事实中确认的升级、备份和故障处理流程，不应直接生成确定性结论，可以标记为建议或待补充内容。

---

## 7. 面向服务器查看与接管

用户通过最终文档应能够快速回答：

> 这台服务器是什么系统和版本？

> CPU、内存和磁盘资源如何？

> 磁盘如何分区和挂载？

> 主要目录分别存放什么？

> 服务器上部署了哪些服务？

> 每个服务是否正在运行？

> 服务部署在哪里？

> 配置、日志和数据在哪里？

> 服务监听哪些端口？

> 服务如何启动、停止和重启？

> 服务器重启后哪些服务会自动启动？

> 哪些信息已经确认，哪些仍需人工补充？

---

## 8. 项目边界

第一阶段重点完成：

* 单台 Linux 服务器探测
* 系统、硬件、网络和存储环境整理
* systemd、进程、端口和常见服务探测
* Docker 和 Docker Compose 探测
* 服务部署目录、配置、日志和数据位置整理
* 生成带事实来源和确定程度的服务器文档

第一阶段不要求：

* 建立完整的服务依赖图
* 还原复杂业务调用链
* 自动发现跨服务器或云平台资源关系
* 自动修改服务器配置
* 自动执行服务启停、升级、备份或故障修复
* 保证识别所有非标准自定义应用

---

### 一句话需求

> 一个 AI 驱动的 Linux 服务器环境与部署服务探测系统，先获取操作系统、硬件、网络、磁盘分区、挂载点和目录情况，再自动发现 systemd、传统进程、Docker/Compose 及常见基础服务，整理每个服务的部署位置、配置、端口、日志、数据和运行方式，并生成便于查看、编辑和接管的 Word 服务器报告。
