# OpSense 需求文档

## 1. 需求结论

### 1.1 现状评估

早期实现已经完成了单台 Linux 服务器的只读采集、结构化快照、脱敏、服务归并、Codex 调用和 Word/HTML 输出，但交付结果仍然偏向“服务器状态摘要”，没有达到“服务器环境与部署服务 Wiki 文档”的目标。

主要问题如下：

1. 报告直接暴露了大量原始采集信息，网络和挂载章节没有完成主机资源与容器内部资源的边界过滤。
2. Docker bridge、veth、overlay、容器 rootfs、临时挂载等运行时噪声与主机网络、主机存储混在一起。
3. 服务信息虽然已经分类，但仍以服务候选列表为中心，缺少面向运维了解和交接的服务知识条目结构。
4. 报告没有形成“服务在哪里部署、如何运行、配置在哪里、日志在哪里、数据在哪里、如何确认”的完整闭环。
5. Codex 当前主要是一次性分析调用，不具备持续观察、提出假设、请求证据、验证结果、修正判断和编辑文档的 Agent 工作流。
6. 原始快照、归一化资产、报告展示对象之间边界不清，导致采集完整性和报告可读性互相牵制。

### 1.2 产品定位

OpSense 定位为：

> 一个以本地 CLI Agent 为主入口、由安全采集器和 Codex Agent 协作完成的 Linux 服务器知识整理工具。

OpSense 的真实产品形态是“可以持续对话和调查的服务器分析 Agent”，而不是一次扫描后生成静态报告的脚本：

* `opsense agent` 是主入口，负责启动、恢复和持续交互的 Agent 会话。
* Codex 是 Agent 的硬依赖；启动 Agent 前必须完成 Codex CLI/SDK、登录状态、模型和 Thread 能力预检。
* Agent 可以围绕同一台服务器连续回答服务、目录、端口、网络、挂载和未知项问题。
* 服务器 Wiki 文档、Word、HTML 和 Markdown 是 Agent 会话中按需生成的知识产物，不是唯一入口。
* `scan`、`analyze`、`report` 和 `inspect` 保留为脚本化、自动化和调试入口。

典型入口：

```bash
opsense agent --host <host> --user <user> --provider codex
opsense agent --scan <scan-id> --provider codex
opsense agent --resume <agent-session-id>
```

核心交付不再是“列出服务器上看到了什么”，而是：

> 在证据可追溯和只读安全边界内，回答这台服务器上有哪些真正需要关注的部署服务、它们分别部署在哪里、如何运行、依赖哪些本地资源、哪些信息还需要人工确认。

### 1.3 基本原则

* 原始采集可以完整，正式报告必须经过独立的业务视图过滤。
* 主机网络、主机存储和部署服务资源是一级对象；容器内部实现细节默认降级为服务附属信息。
* 服务器 Wiki 文档优先于命令输出，事实、推断、未知和建议必须分开。
* Codex Agent 只能通过本地结构化工具工作，不能自由执行 Shell，不能直接登录服务器。
* Agent 可以提出补充探测，但每次补探测必须经过本地安全策略、预算和证据来源校验。
* AI 不能删除原始事实，也不能把推断写成确定事实。
* 报告必须服务于查看、交接和运维了解，不以展示采集数量为目标。
* Codex 不可用时不得启动 Agent 或生成伪装成完整 Agent 结果的 Wiki 文档。

## 2. 目标与非目标

### 2.1 建设目标

OpSense 必须完成以下目标：

1. 生成干净的主机环境与资源视图。
2. 过滤 Docker、容器运行时和系统内部噪声，避免污染主机网络和主机挂载章节。
3. 形成主要部署服务清单、支撑组件清单和系统服务摘要。
4. 为每个重要服务生成可阅读、可追溯的服务知识条目。
5. 通过 Agent 多轮分析补足非标准服务、非标准目录和缺失证据。
6. 让 Word 和 HTML 报告具备正式交付质量，而不是简单的状态表格集合。
7. 保留原始快照和完整证据，确保报告过滤不会造成数据丢失。
8. 提供可通过 CLI 持续追问、调查和生成服务器 Wiki 文档的 Agent 会话。

### 2.2 非目标

OpSense 仍然不做以下内容：

* 完整的跨服务业务依赖图或调用链还原。
* 自动修改服务器配置、启动、停止、升级、备份或修复服务。
* 批量服务器管理平台、用户系统、Web 管理后台和中心化任务调度。
* 无限制的全盘文件内容索引。
* 让 AI 直接连接 SSH 或执行任意远程命令。
* 将“配置中出现的地址”强行解释成已经验证的服务依赖。
* 保证识别所有自研程序的业务含义；无法确认时必须明确标记未知。

## 3. 核心用户场景

### 3.1 新接手服务器

用户输入一台服务器的 SSH 信息，得到一份可以交给下一位运维人员查阅的服务器 Wiki 文档，能够快速回答：

* 服务器是什么系统、版本和运行环境？
* 主机有多少 CPU、内存、磁盘和有效挂载点？
* 哪些目录是真正的部署目录、数据目录、日志目录和备份目录？
* 服务器上有哪些主要部署服务？
* 每个服务使用什么部署方式？
* 每个服务如何启动、停止、重启和查看日志？
* 服务配置、环境文件、数据和日志分别在哪里？
* 哪些端口对外暴露，哪些只是容器内部端口？
* 哪些结论已经确认，哪些结论仍然需要人工核对？

### 3.2 服务器交接和变更前盘点

用户使用已有快照重新生成报告，或让 Agent 针对指定服务进行二次核验，不需要重新扫描整台服务器。

### 3.3 非标准服务识别

服务器出现 Doris、Hadoop、MinIO、RustFS、FastDFS、企业自研程序或不常见目录时，系统不应只依赖固定名称规则，而应根据进程、镜像、端口、目录、配置文件和启动方式形成证据假设，并在必要时提出受限补探测。

### 3.4 CLI Agent 交互

用户在同一个 Agent 会话中连续追问，Agent 根据已有证据和受控补探测逐步完善判断：

```text
你：这台服务器上有哪些主要部署服务？
Agent：列出服务知识条目，并说明证据覆盖率和待确认项。

你：详细分析 minio，包括部署目录、端口、数据目录和配置文件。
Agent：读取相关证据，必要时发起受控补探测并更新该服务条目。

你：生成服务器 Wiki 文档。
Agent：执行质量检查并输出 Word、HTML、Markdown 路径。
```

交互会话必须支持自然语言问题、固定命令、实时阶段和工具调用摘要，以及通过会话 ID 恢复上下文。

## 4. 输出物定义

### 4.1 输出物分层

输出物拆分为三层：

```text
原始采集快照
  -> 归一化资产与证据图
    -> 报告展示投影
      -> 服务器 Wiki 文档
```

* 原始采集快照：尽可能保留采集事实、命令状态、原始证据引用和未知项。
* 归一化资产：将主机、磁盘、挂载、网络、进程、容器、配置和服务统一为可关联对象。
* 报告展示投影：根据资源类型、服务关联和可见性策略决定哪些内容进入正文、摘要或附录。
* 服务器 Wiki 文档：把报告投影重新组织为服务器知识概览、服务知识条目和证据附录。

### 4.2 报告正式章节

Word 和 HTML 必须包含以下章节：

1. **执行摘要**
   * 服务器身份、系统版本和扫描时间。
   * 主要部署服务数量和服务类型分布。
   * 对外监听端口概况。
   * 存储容量和高风险项。
   * 信息完整度、主要未知项和需要人工确认的事项。

2. **服务器环境**
   * 主机名、IP、发行版、Kernel、架构、虚拟化环境。
   * CPU、内存、Swap、时区、运行时间。
   * 软件包管理器和关键运行时版本。
   * 用户权限和 sudo 能力摘要。

3. **主机网络**
   * 物理或虚拟主机网卡。
   * 主机 IP、默认路由、DNS 和防火墙摘要。
   * 主机对外监听端口及其关联服务。
   * 网络接口用途和判断依据。

4. **主机存储与目录布局**
   * 物理磁盘、分区、LVM/RAID 和文件系统。
   * 有效主机挂载点、容量、使用率和读写属性。
   * `/opt`、`/srv`、`/data`、`/app`、`/var/www` 等部署目录用途。
   * 数据、日志、备份和临时目录的识别结果。

5. **主要部署服务总览**
   * 服务名称、用途、角色、状态、部署方式、对外端口。
   * 服务所在部署目录。
   * 报告章节链接和信息完整度。

6. **服务知识条目**
   * 每个主要服务单独一个章节。
   * 详细字段见第 7 节。

7. **支撑组件**
   * 数据库、中间件、反向代理、消息组件、容器平台等。
   * 只展示与部署服务有直接关系或对外提供能力的组件。

8. **系统服务摘要**
   * systemd 服务总数、运行数、停止数、失败数。
   * 失败服务、对外监听服务、自定义路径服务和与主要部署服务相关的服务。
   * 普通发行版自带服务只显示汇总，不逐条生成详情。

9. **风险与待确认事项**
   * 端口暴露、磁盘空间、服务失败、路径缺失、配置缺失、权限不足。
   * AI 无法确认的用途、目录归属、启停方式和数据位置。
   * 因安全策略或预算未执行的补探测。

10. **证据附录**
    * 重要结论与 Evidence ID 的对应关系。
    * 采集时间、命令来源、状态和脱敏说明。
    * 原始候选、被过滤对象和过滤原因的统计，不把全部噪声展开到正文。

### 4.3 报告内容质量要求

* 正文不显示无业务意义的容器网络和容器根文件系统挂载。
* 正文不显示普通发行版 systemd 服务的逐条详情。
* 任何服务章节必须有“已确认信息、合理推断、未知和建议核验”四类边界。
* 每个主要服务必须能回溯到至少一个进程、unit、容器、端口、目录或配置证据。
* 没有可靠证据的启动、停止、重启命令只能标记为“未确认”，不能凭经验生成确定结论。
* 报告应优先展示少量重要服务，不以候选总数或采集记录数作为主要指标。

## 5. 主机网络过滤需求

### 5.1 网络资源分类

采集层可以保留完整网络事实，但报告层必须将网络对象分为：

* `host_interface`：主机物理网卡、虚拟网卡和主机 IP。
* `host_route`：主机路由、默认网关和 DNS。
* `published_service_port`：从主机对外可访问地址映射到服务的端口。
* `container_network`：Docker bridge、overlay、veth、容器内部网络和 Compose 网络。
* `internal_runtime_network`：容器运行时、服务网格或本机内部通信网络。
* `unknown_network`：无法判断用途的网络对象。

### 5.2 默认展示规则

* 主机网络章节只展示 `host_interface`、`host_route` 和 `published_service_port`。
* Docker bridge、overlay、veth 和 Compose 网络默认不进入主机网络正文。
* 容器网络只有在以下条件之一满足时，才作为对应服务的附属信息展示：
  * 服务通过该网络对外发布端口。
  * 多个主要服务通过该网络直接关联。
  * Agent 判断该网络是服务运行所必需的，并且有证据支持。
* 容器网络详细表放入可选附录，不在主机网络摘要中平铺。
* `0.0.0.0` 或主机真实 IP 上的发布端口应进入服务知识条目和主机暴露面摘要。
* 仅容器内部的 `containerPort` 不应被表述为主机对外端口。

### 5.3 验收标准

在包含大量 Docker/Compose 网络的样本服务器上：

* 主机网络正文不出现 veth、docker bridge、overlay 等内部网络对象。
* 每个对外发布端口至少能关联到一个服务或进入待确认列表。
* 容器内部端口和主机映射端口分别展示，不混为一个端口。

## 6. 主机存储和挂载过滤需求

### 6.1 存储资源分类

挂载和存储对象必须标记用途：

* `host_block_device`：真实磁盘、分区、LVM、RAID 和主机文件系统。
* `host_mount`：主机有效挂载点。
* `service_data_mount`：明确属于某个部署服务的数据挂载。
* `service_log_mount`：明确属于某个部署服务的日志挂载。
* `service_backup_mount`：明确属于某个部署服务或主机的备份挂载。
* `container_rootfs`：容器 overlay/rootfs 层。
* `container_runtime_mount`：Docker、containerd、Podman 运行时内部挂载。
* `pseudo_filesystem`：`proc`、`sysfs`、`devtmpfs`、`cgroup`、`tmpfs` 等伪文件系统。
* `temporary_runtime_mount`：shm、临时目录、运行时 socket 等短生命周期挂载。
* `unknown_mount`：无法确认用途的挂载。

### 6.2 默认展示规则

* 主机存储正文只展示真实块设备、主机有效挂载点和有明确业务用途的服务数据/日志/备份挂载。
* 以下对象默认从正文过滤：
  * Docker overlay2 和容器 rootfs。
  * Docker/containerd 内部 metadata 和 layer 挂载。
  * `/proc`、`/sys`、`/dev`、`/run` 下伪文件系统。
  * 容器 shm、匿名临时挂载和运行时 socket 挂载。
* 服务章节可以展示服务实际使用的宿主机源路径，但必须显示“宿主机路径 -> 容器路径”的映射关系。
* Docker named volume 只有在能关联到主要服务并能说明用途时，才在对应服务知识条目中展示。
* 无法确认用途的挂载进入附录统计和待确认事项，不在正文平铺。

### 6.3 去重规则

* 同一宿主机路径不能在主机存储和多个服务章节中重复展开无意义的完整信息。
* 容器 rootfs 不得被当作独立磁盘、分区或部署目录。
* 服务挂载信息只显示源路径、目标路径、读写属性和用途，不展开容器内部全部挂载列表。

### 6.4 验收标准

在包含 Docker、Compose、overlay2 和大量 volume 的样本服务器上：

* 主机存储正文不出现容器 rootfs、overlay2、shm 和伪文件系统噪声。
* 有业务意义的宿主机数据目录仍然可追溯到对应服务。
* 每个服务挂载映射能够区分宿主机路径和容器路径。

## 7. 服务知识条目需求

### 7.1 服务对象定义

服务不是单一进程或单一容器，而是由以下证据合并形成的部署单元：

```text
服务
  |- 业务用途
  |- 部署方式
  |- systemd unit / Compose service / container / process
  |- 部署目录
  |- 配置和环境文件
  |- 主机暴露端口
  |- 数据、日志和备份位置
  |- 启停方式
  `- 证据、置信度和待确认事项
```

### 7.2 服务分类

服务至少分为：

* `primary_application`：业务应用、自研程序、面向用户的 Web/API/Worker。
* `infrastructure_service`：数据库、缓存、消息队列、对象存储、搜索、注册中心等。
* `edge_service`：Nginx、Caddy、HAProxy、网关和反向代理。
* `supporting_component`：与主要服务直接相关的辅助组件。
* `container_platform`：Docker、containerd 等运行平台，只做平台摘要。
* `system_service`：操作系统服务，只在系统服务摘要或异常列表展示。
* `needs_review`：证据不足或存在冲突的候选。

### 7.3 单个服务知识条目字段

每个 `primary_application` 和与其直接相关的基础设施服务必须生成独立手册，至少包含：

1. 服务名称、显示名称和用途。
2. 服务角色和用途判断理由。
3. 当前状态、健康线索和最近采集时间。
4. 部署方式：systemd、Compose、Docker、直接进程或未知。
5. 部署目录和目录用途。
6. systemd unit、Compose 文件、容器名称和镜像。
7. 配置文件、环境文件和配置摘要。
8. 主机监听地址、主机端口、容器端口和端口暴露范围。
9. 数据目录、日志目录、备份目录和宿主机挂载。
10. 启动、停止、重启和日志查看方式：只记录有证据支持的命令或入口。
11. 开机自启动、容器重启策略和运行用户。
12. 关联服务或本地资源观察结果，不强制形成业务依赖图。
13. 已确认事实、合理推断、未知信息和建议核验项。
14. Evidence ID、来源命令和来源路径。

### 7.4 服务知识条目可读性要求

* 服务章节开头先给出一句话用途和知识摘要。
* 路径、端口、配置、日志和启停入口采用固定版式，便于扫描和复制。
* 不把完整原始环境变量、完整容器 mount 列表和系统 unit 列表直接贴入正文。
* 对同一服务的多个容器、进程和 Compose service 进行合并展示。
* 对证据冲突给出明确提示，不隐式选择一个结果。
* 没有证据的字段显示“未确认”，而不是留空或猜测。

## 8. Codex Agent 需求

### 8.1 从 Provider 到 Agent

旧版的 `AiProvider.analyze()` 是一次调用，当前实现需要改为有状态的 Agent 会话。Agent 的职责不是直接替代采集器，而是围绕证据完成以下循环：

```text
建立上下文
  -> 形成服务和路径假设
  -> 检查证据覆盖率
  -> 提出结构化补探测
  -> 本地策略校验与执行
  -> 合并新证据并重新归一化
  -> 验证或推翻原假设
  -> 生成服务器 Wiki 文档和风险清单
  -> 质量审查与收敛
```

### 8.2 Agent 角色

逻辑上至少包含以下角色，可以在同一个 Codex thread 中通过阶段提示实现，也可以后续拆成多个子 Agent：

1. **Inventory Analyst**：理解主机环境、磁盘、主机网络和运行时资源。
2. **Service Detective**：从进程、unit、容器、端口、目录和配置线索识别部署服务。
3. **Path Investigator**：处理非标准目录、未知路径和部署文件位置。
4. **Evidence Reviewer**：检查每个重要结论是否有证据，发现冲突和过度推断。
5. **Wiki Editor**：将确认后的服务信息编排成服务器 Wiki 文档。
6. **Report QA Reviewer**：检查正文噪声、章节完整度、过滤结果和事实边界。

### 8.3 Agent 工具边界

Agent 只能调用本地暴露的结构化工具：

* `read_snapshot_section`：读取脱敏快照指定章节。
* `read_evidence`：读取指定 Evidence 的摘要和来源。
* `list_service_candidates`：获取服务候选及当前分类状态。
* `request_directory_metadata`：申请已知目录元数据。
* `request_directory_listing`：申请受限目录列表。
* `request_config_summary`：申请已知配置文件结构摘要。
* `request_path_search`：在批准根目录和证据来源范围内搜索路径名称。
* `get_probe_policy`：查看剩余探测预算和拒绝原因。
* `build_report_draft`：生成中间报告投影。
* `review_report_draft`：执行本地报告质量规则。

Agent 禁止：

* 生成任意 Shell 字符串。
* 直接调用 SSH、网络请求、文件系统写入或服务器登录。
* 读取未脱敏原始环境变量和密钥。
* 修改快照原始事实。
* 自行扩大搜索根目录、深度、命中数或读取预算。

### 8.4 Agent 状态

每次 Agent 会话必须持久化以下状态：

* `sessionId`、scan ID、thread ID 和 provider。
* 当前阶段和阶段历史。
* 当前服务假设、路径假设和置信度。
* 假设引用的 Evidence ID。
* 已提出、已接受、已执行、失败和跳过的 ProbeRequest。
* 被过滤的网络、挂载和系统服务对象及其原因。
* 当前报告草稿和质量检查结果。
* Agent 未解决的问题和下一步建议。
* token、时间、请求数和预算消耗。

### 8.5 Agent 收敛条件

Agent 不应无限循环。满足以下任一条件时结束：

* 所有主要服务均有最低证据覆盖率。
* 没有新的安全允许补探测请求。
* 达到最大 Agent 轮数或时间预算。
* 连续两轮没有产生新的有效证据或分类变化。
* Codex Thread 创建、恢复或调用失败，经过有限重试后将会话置为 `failed`，保留现场供用户修复环境后恢复。

### 8.6 Agent 输出契约

Agent 每一轮必须输出结构化结果：

```text
AgentTurn
  |- observations
  |- hypotheses
  |- evidenceGaps
  |- probeRequests
  |- acceptedDecisions
  |- rejectedDecisions
  |- reportChanges
  |- unresolvedQuestions
  `- nextAction
```

最终结果必须拆分为：

* `InventoryProjection`：主机环境、主机网络、主机存储和目录布局。
* `ServiceWikiEntry[]`：服务知识条目。
* `VisibilityDecision[]`：对象展示、摘要或过滤决定。
* `RiskFinding[]`：风险和待确认项。
* `AgentSession`：完整的 Agent 过程和审计记录。

## 9. 数据模型变更需求

### 9.1 资源可见性

所有网络、挂载、系统服务和容器运行时对象必须增加报告投影属性：

```text
visibility: primary | supporting | summary | appendix | filtered
visibilityReason: string
resourceClass: string
relatedServiceIds: string[]
evidenceIds: string[]
```

`filtered` 不代表删除，原始对象仍保留在快照和过滤统计中。

### 9.2 服务知识条目模型

新增 `ServiceWikiEntry`，至少包括：

```text
ServiceWikiEntry
  |- serviceId
  |- identity
  |- purpose
  |- role
  |- lifecycle
  |- deployment
  |- exposure
  |- configuration
  |- storage
  |- logging
  |- evidence
  |- confidence
  |- unknowns
  `- reviewItems
```

### 9.3 Agent 会话模型

新增 `AgentSession`、`AgentTurn`、`AgentHypothesis`、`VisibilityDecision`、`ReportReview` 和 `ProbeBudget` 等结构化对象，并对每次 Agent 调用、工具调用、补探测和报告修改建立关联。

### 9.4 原始数据与报告投影隔离

报告生成器不得直接从原始 `snapshot.services`、`snapshot.storage.mounts` 或 `snapshot.network.interfaces` 平铺输出。必须先生成：

```text
Snapshot
  -> InventoryProjection
  -> ServiceWikiProjection
  -> ReportModel
```

任何过滤必须产出理由和统计信息。

## 10. 架构调整需求

### 10.1 新的本地架构

```text
CLI
  -> Scan Orchestrator
    -> Read-only SSH Collector
      -> Raw Snapshot
        -> Normalizer / Evidence Graph
          -> Resource Filter
            -> Codex Agent Runtime
              -> Controlled Probe Executor
                -> Service Wiki Builder
                  -> Report QA
                    -> 服务器 Wiki 文档（Word / HTML / Markdown）
```

### 10.2 模块职责

* `collector`：只负责读取和解析，不决定报告展示。
* `normalizer`：负责对象归并、关系和证据引用。
* `resource-filter`：负责主机网络、主机存储、容器内部资源和系统服务降噪。
* `agent-runtime`：负责 Codex thread、阶段状态、工具调用、预算和收敛。
* `probe-governor`：负责补探测校验、执行和审计。
* `wiki-builder`：负责服务知识条目字段和完整度评分。
* `report-projection`：负责章节、排序、正文/摘要/附录/过滤展示。
* `report-renderer`：只负责 Word、HTML 和 Markdown 渲染，不再承担业务分类。

### 10.3 CLI 调整

`opsense agent` 是主入口；现有命令保留为脚本化和调试入口：

```bash
# 启动交互式 Agent 并完成扫描
opsense agent --host <host> --user <user> --provider codex

# 基于已有扫描进入交互式 Agent
opsense agent --scan <scan-id> --provider codex

# 恢复已有 Agent 会话
opsense agent --resume <agent-session-id>

# 非交互单轮 Agent
opsense agent --scan <scan-id> --prompt "列出对外暴露的主要服务" --once
```

脚本化入口：

```bash
# 只做采集和本地归一化
opsense scan --host <host> --user <user>

# 运行离线 Agent，不连接服务器
opsense analyze --scan <scan-id> --provider codex

# 只根据最终投影重新生成报告
opsense report --scan <scan-id> --format docx,html

# 完成采集、Agent、补探测、手册和报告
opsense inspect --host <host> --user <user> --provider codex
```

建议新增参数：

* `--max-agent-rounds`：Agent 最大轮数。
* `--max-probes`：补探测请求数上限。
* `--focus-service <service>`：只针对指定服务深化服务知识条目。
* `--include-appendix`：显示被过滤资源统计和详细附录。
* `--report-profile wiki|summary|audit`：选择 Wiki、摘要或审计视图。
* `--resume-agent <session-id>`：继续未完成的 Agent 会话（兼容参数）。
* `--prompt <text>`：启动时提交一条自然语言问题。
* `--once`：只执行一轮并输出结果，不进入 REPL。
* `--resume <agent-session-id>`：恢复 Agent 会话的快捷形式。
* `--focus-service <service-id>`：将调查重点限定到指定服务。

交互式固定命令：`status`、`services`、`show <service-id>`、`review`、`wiki`、`resume`、`exit`。

## 12. 验收标准

### 12.1 资源过滤

* 主机网络正文不出现 Docker bridge、veth、overlay 和容器内部网络。
* 主机存储正文不出现 overlay2、容器 rootfs、shm、proc、sysfs 和运行时临时挂载。
* 容器服务的宿主机数据挂载仍然能够在对应服务知识条目中准确展示。
* 所有被过滤对象均可在审计附录中按类别和原因统计。

### 12.2 服务知识条目

* 主要部署服务不再仅显示一行摘要，而是生成独立的服务知识章节。
* 每个主要服务至少覆盖：用途、状态、部署方式、部署目录、端口、配置、日志、数据、生命周期和证据。
* 缺失字段显示“未确认”，并进入待确认事项。
* 普通 Linux systemd 服务不逐条生成主要服务详情。

### 12.3 Agent 能力

* Agent 至少完成“观察 -> 假设 -> 证据缺口 -> 受控补探测 -> 验证 -> 手册生成”的闭环。
* Agent 过程可以恢复，且每次工具调用和决策都有审计记录。
* `opsense agent --scan <scan-id>` 可以进入交互会话，同一 session 至少连续回答三个问题。
* `wiki` 命令可以在会话内生成服务器 Wiki 文档，并返回 Word、HTML、Markdown 路径。
* Agent 会话可以通过 session ID 恢复，恢复后不重复执行已成功的补探测。
* Agent 不得调用任意 Shell、访问网络或直接登录服务器。
* Codex 不可用时，Agent 预检必须失败并给出明确修复提示；不生成 Agent Wiki 文档。

### 12.4 报告交付

* Word 和 HTML 章节结构一致，均以服务器 Wiki 文档为主。
* 报告正文适合人工阅读，原始证据和被过滤资源进入附录。
* 报告中所有重要结论都可以追溯到 Evidence ID。
* 同一个扫描快照可以重复生成 Wiki 版、摘要版和审计版报告，不需要重新连接服务器。

## 13. 风险与决策

### 13.1 风险

* Agent 轮数增加会提高 Codex 调用耗时和成本。
* 资源过滤错误可能隐藏真正重要的服务挂载或端口。
* 非标准服务识别仍然存在证据不足问题。
* 服务生命周期命令容易被 AI 过度推断，必须坚持证据门禁。
* Word 手册章节数量增加后，需要控制文档长度和索引体验。

### 13.2 决策

* 采集完整性和报告可读性分离解决，不通过减少采集来解决报告噪声。
* 过滤规则由确定性策略负责，Codex Agent 负责语义判断和缺口验证，不让模型单独决定安全边界。
* Agent 首期最多执行有限轮数的补探测，默认仍以一次补探测轮为安全上限；多轮能力通过显式参数开启。
* Codex 是 Agent 的硬依赖；本地基线分类只能作为上下文准备和测试替身，不能作为 Agent 的最终结果。
* 服务知识条目优先覆盖主要部署服务和直接相关支撑组件，普通系统服务只做摘要。
* 先完成报告投影和服务知识条目，再扩大 Agent 自主性；没有稳定的报告契约，Agent 轮数增加只会放大噪声。

## 14. 一句话需求

> OpSense 不再只是把服务器扫描结果和一次 Codex 分析拼成报告，而是通过 `opsense agent` 提供可恢复的 CLI 对话和调查能力；Agent 在独立的资源过滤、服务证据归并和安全补探测边界内，将主机环境、有效存储和服务器重要服务整理成事实可追溯、噪声可控、便于持续查阅的服务器 Wiki 文档，并按需输出 Word、HTML 和 Markdown 格式。
