# OpSense 技术方案 v3.0

## 1. 文档目的

本文给出 OpSense v3.0 的可实施技术方案，包括扫描阶段、批量命令、资源关联、候选筛选、Codex 批量契约、受控补探测、持久化、CLI、测试与发布计划。

总体架构和架构决策见 [架构设计 v3.0](./架构设计v3.0.md)。

v3.0 作为未正式发布项目的全新主线实现，不兼容旧版数据、CLI、工作区、Projection 或 Agent Session。实施时允许直接删除、移动或重写现有模块，不建设版本迁移层。

## 2. 建设目标

### 2.1 核心目标

1. 在一分钟内优先产出可用的服务器部署线索清单。
2. 将 SSH 命令从逐对象 N+1 查询改为固定基线加批量详情查询。
3. 将正常 Codex 应用层调用从几十轮降低到 2～3 次。
4. 通过确定性关联减少模型需要处理的候选数量。
5. 对目录、配置和日志使用一次批量按需补探测，而不是默认全量读取。
6. 让扫描、部署发现、Wiki 生成和交互式调查可以独立运行与恢复。
7. 延续已经验证有效的只读、安全、脱敏、证据追溯和报告质量原则，但不保留旧接口和旧数据结构。

### 2.2 非目标

- 不自动修改、启停、升级或修复服务器服务。
- 不建立完整跨服务器 CMDB 或调度平台。
- 不保证还原业务调用链。
- 不进行无限制全盘搜索或文件内容索引。
- 不允许 Codex 生成任意远程 Shell。
- 不以固定产品名称规则替代最终语义判断。

## 3. 交付范围

v3.0 首期交付：

- `fast`、`standard`、`deep` 三种扫描 profile。
- 共享 SSH Collection Scheduler。
- systemd 和 Docker 批量详情采集。
- Resource Graph 和 Deployment Candidate。
- 本地高价值候选保护与系统对象聚合。
- Codex 批量发现契约。
- 单轮批量受控补探测。
- Deployment Inventory 与 Wiki Projection 分离。
- 可恢复阶段产物与性能指标。
- 基于报告的交互式 Agent。

## 5. 工作流设计

### 5.1 Pipeline 状态机

```text
created
  -> preflighting
  -> collecting_baseline
  -> correlating
  -> inventory_ready
  -> discovering
  -> probing          (可选)
  -> reconciling      (可选)
  -> composing
  -> reporting
  -> completed

任意阶段
  -> partial
  -> failed
  -> interrupted
```

状态语义：

- `inventory_ready`：已存在可用的本地证据型部署清单。
- `partial`：当前阶段未完全成功，但已有产物可以恢复或查看。
- `failed`：当前请求失败，不代表已经持久化的前序产物失效。
- `completed`：所选 profile 的全部完成门禁通过。

### 5.2 阶段依赖

| 阶段 | 输入 | 输出 | 是否需要 SSH | 是否需要 Codex |
| --- | --- | --- | --- | --- |
| Preflight | CLI 参数、配置 | 能力与权限 | 是 | 可并行检查 |
| Baseline Collection | SSH 能力 | Raw Evidence | 是 | 否 |
| Correlation | Raw Evidence | Resource Graph | 否 | 否 |
| Candidate Selection | Resource Graph | Deployment Candidates | 否 | 否 |
| Batch Discovery | Candidates | Discovery Result | 否 | standard/deep 需要 |
| Governed Probe | Probe Plan | New Evidence | 是 | 否 |
| Reconciliation | Candidates + New Evidence | Final Discovery Result | 否 | 有 Probe 时需要 |
| Wiki Composition | Deployment Inventory | Wiki Projection | 否 | 正式语义版需要 |
| Report | Wiki Projection | HTML/DOCX/Markdown | 否 | 否 |

### 5.3 运行策略

SSH 预检与 Codex 预检可以并行。Codex 预检失败不得阻止 Baseline Collection；它只影响语义发现与正式 AI Wiki。

每完成一个阶段立即原子持久化。后续失败时，用户至少可以查看最后一个稳定阶段的产物。

## 6. Collection Scheduler

### 6.1 任务模型

```ts
interface CollectionTask<T> {
  taskId: string;
  commandId: string;
  parameters: Record<string, string | number | boolean | string[]>;
  priority: "critical" | "normal" | "enrichment";
  dependencies: string[];
  timeoutMs: number;
  maxOutputBytes: number;
  cacheKey: string;
  parse(result: CommandExecutionResult): T;
}
```

### 6.2 调度规则

- 全局默认最多 4 个 SSH channel。
- `critical` 任务优先于目录和配置任务。
- 单个任务失败不取消无依赖任务。
- 同一 `cacheKey` 在一次 ScanRun 内只执行一次。
- AbortSignal、命令超时和总工作流超时同时生效。
- 输出达到限制时关闭远端 channel，并保存 `truncated`。
- 命令完成和审计写入解耦；审计采用单写队列，但不得阻塞其他 SSH channel 调度。

### 6.3 缓存键

缓存键必须由规范化后的语义请求计算：

```text
sha256(commandSpecVersion + commandId + normalizedParameters + sudoMode)
```

不同 Probe Request ID 但命令和参数相同，应复用同一执行结果。

### 6.4 自适应并发

默认并发为 4。当远端返回 channel open failure、资源不足或连续超时时，降低为 2；稳定完成一段时间后可恢复，但不得超过配置上限。

## 7. 快速采集方案

### 7.1 基线命令组

基线命令仍保持固定白名单，建议分为以下组：

1. 身份与权限：UID、用户、组、sudo 能力。
2. 主机：OS、Kernel、架构、主机名、时区、CPU、内存、虚拟化。
3. 存储：块设备、挂载、容量、inode、fstab、swap。
4. 网络：地址、路由、DNS、防火墙摘要、监听 socket。
5. 运行态：进程列表、进程 cwd/exe/cgroup、systemd 摘要。
6. 容器：Docker/Compose 摘要和批量详情。

M3 与 M4 不再作为完全串行的大阶段，除发行版降级链外，其余无依赖任务统一进入 Scheduler。

### 7.2 systemd 批量查询

现状是一次 wildcard 查询后，对未覆盖 unit 逐个执行 `systemctl show`。v3.0 改为：

1. 获取 loaded unit 和 unit-file 名称集合。
2. 按 unit 名排序、去重。
3. 每 32～64 个 unit 生成一个安全批量任务。
4. 执行：

```text
systemctl show <unit-1> <unit-2> ... <unit-n> \
  --all --no-pager \
  --property=Id \
  --property=Description \
  --property=LoadState \
  --property=ActiveState \
  --property=SubState \
  --property=UnitFileState \
  --property=MainPID \
  --property=FragmentPath \
  --property=WorkingDirectory \
  --property=ExecStart \
  --property=EnvironmentFiles \
  --property=User \
  --property=Group
```

命令规格接受经过正则校验的 `unitNames: string[]`，并限制数组长度。解析结果按 `Id` 返回对象级成功或缺失状态。

`fast` profile 可以只详细查询：

- active、failed unit。
- `/etc/systemd/system` 和 `/usr/local/lib/systemd/system` 下的自定义 unit。
- 与监听进程存在确定关联的 unit。

其他 unit 保留列表级证据并进入系统摘要。

### 7.3 Docker 批量查询

获取容器 ID 后，按 32～64 个分块执行：

```text
docker inspect <id-1> <id-2> ... <id-n>
```

容器 ID 逐项验证为 12～64 位十六进制字符串。解析时为每个容器产生独立对象和 Evidence 关联，整批命令失败时再按二分策略定位失败对象，最多增加对数级重试，不直接退化为全部逐个执行。

### 7.4 进程路径采集

保留一次 `/proc` cwd/exe 链接扫描，但结果只作为路径线索。快速扫描不对每个路径执行 `find`。

优先采集以下进程：

- 持有监听 socket。
- systemd MainPID 或其子进程。
- 容器 init PID。
- 可执行路径位于自定义目录。
- 长期运行且命令形态类似服务。

其他进程只保留基础 ps 证据。

### 7.5 路径元数据

初始扫描只对已经明确关联高价值对象的路径执行批量 `stat`。使用 `stat` 的多路径参数，一次处理最多 64 个路径。

默认不在初始扫描中读取配置内容。

## 8. 路径归一化与合并

### 8.1 路径分类

路径先分类为：

- `file_candidate`
- `directory_candidate`
- `mount_source`
- `runtime_internal`
- `system_managed`
- `forbidden`
- `unknown`

配置扩展名只能作为 `file_candidate` 提示，最终以 `stat` 为准。

### 8.2 祖先路径压缩

构建路径 Trie：

```text
/opt/app
|-- conf
|   `-- application.yml
`-- logs
```

若计划扫描 `/opt/app` 深度 3，则覆盖范围内的 `/opt/app/conf` 和 `/opt/app/conf/application.yml` 不再生成独立目录扫描任务。文件仍可根据策略生成独立配置摘要请求。

压缩规则必须考虑：

- 是否跨文件系统。
- 祖先请求深度是否覆盖子路径。
- 子路径是否需要不同权限或读取类型。
- 禁止目录不能因祖先扫描被间接包含。

### 8.3 全局预算

```ts
interface PathBudget {
  maxRoots: number;
  maxDepth: number;
  maxEntriesPerRoot: number;
  maxTotalEntries: number;
  maxConfigFiles: number;
  maxConfigBytes: number;
  maxTotalBytes: number;
  maxDurationMs: number;
}
```

`standard` 建议默认：

| 参数 | 默认值 |
| --- | ---: |
| `maxRoots` | 20 |
| `maxDepth` | 2 |
| `maxEntriesPerRoot` | 500 |
| `maxTotalEntries` | 3000 |
| `maxConfigFiles` | 30 |
| `maxConfigBytes` | 128 KiB |
| `maxTotalBytes` | 5 MiB |
| `maxDurationMs` | 60 秒 |

## 9. Resource Graph

### 9.1 节点类型

```ts
type ResourceNode =
  | HostNode
  | SystemdUnitNode
  | ProcessNode
  | SocketNode
  | ContainerNode
  | ComposeProjectNode
  | MountNode
  | PathNode;
```

### 9.2 边类型

```ts
type ResourceEdgeKind =
  | "unit_main_process"
  | "process_parent"
  | "process_socket"
  | "process_cgroup_unit"
  | "process_container"
  | "container_compose_service"
  | "container_publishes_port"
  | "container_mounts_path"
  | "unit_references_path"
  | "process_references_path"
  | "path_on_mount";
```

每条边至少包含：

```ts
interface ResourceEdge {
  edgeId: string;
  kind: ResourceEdgeKind;
  fromId: string;
  toId: string;
  confidence: "confirmed" | "inferred";
  ruleId: string;
  evidenceIds: string[];
}
```

### 9.3 归并算法

使用 Union-Find 或连通分量构建初始部署组，但以下边不能自动强归并：

- 仅共享同一 mount。
- 仅使用相同运行时语言。
- 仅名称相似。
- 仅配置中出现相同地址。

强关联边包括：

- unit MainPID -> process。
- process cgroup -> unit/container。
- container -> Compose service/project。
- host published port -> container。

弱关联边只作为 Candidate 的提示，由 Codex 决定是否合并。

## 10. Deployment Candidate

### 10.1 数据契约

```ts
interface DeploymentCandidate {
  candidateId: string;
  sourceObjectIds: string[];
  suggestedName?: string;
  deploymentHints: Array<"systemd" | "process" | "docker" | "compose">;
  unitIds: string[];
  processIds: string[];
  socketIds: string[];
  containerIds: string[];
  composeProjectIds: string[];
  pathIds: string[];
  imageNames: string[];
  exposedPorts: PortSummary[];
  protectionSignals: ProtectionSignal[];
  evidenceIds: string[];
  unresolvedFields: string[];
}
```

### 10.2 候选保护规则

以下对象不得进入普通系统聚合组：

- 任意 Docker/Compose 对象。
- 监听非 loopback 地址的服务。
- 持有监听 socket 的未知进程。
- failed unit。
- 自定义 unit 路径。
- 自定义执行路径、工作目录或数据路径。
- 与服务数据、日志、备份挂载关联的对象。
- 存在证据冲突的对象。

### 10.3 系统对象聚合

聚合结果示例：

```ts
interface FilteredEvidenceGroup {
  groupId: string;
  category:
    | "routine_system_service"
    | "boot_helper"
    | "kernel_helper"
    | "runtime_internal"
    | "inactive_unit";
  objectCount: number;
  sourceObjectIds: string[];
  sampleNames: string[];
  reason: string;
  evidenceIds: string[];
}
```

聚合是报告与 AI 输入优化，不删除 Raw Evidence，后续 Agent 可以重新提升某个对象。

## 11. Codex 批量发现

### 11.1 调用模型

v3.0 不再采用“一轮一个工具”的主流程。应用层调用定义为：

```text
Call 1: classify_and_merge(candidates)
Call 2: reconcile_with_probe_results(...)   # 可选
Call 3: compose_wiki(inventory)
```

### 11.2 输入压缩

首次调用只输入：

- 主机摘要。
- 高价值 Candidate 列表。
- 聚合系统对象统计。
- 每个 Candidate 的关键 unit、命令、镜像、端口、路径和 Evidence ID。
- 已知冲突和未知字段。
- Probe 类型和预算摘要。

不输入：

- 完整 Snapshot。
- 普通 unit 全量详情。
- 完整进程表。
- 完整配置内容。
- 已过滤容器网络和 rootfs mount。

### 11.3 输出契约

```ts
interface BatchDiscoveryDecision {
  decisionId: string;
  sourceCandidateSetHash: string;
  services: DiscoveredServiceDraft[];
  filteredCandidateIds: string[];
  retainedUnknownCandidateIds: string[];
  probeRequests: ProbeRequest[];
  unresolvedQuestions: string[];
  summary: string;
}

interface DiscoveredServiceDraft {
  serviceId: string;
  name: string;
  displayName?: string;
  role:
    | "primary_application"
    | "infrastructure_service"
    | "edge_service"
    | "supporting_component"
    | "container_platform"
    | "system_service"
    | "needs_review";
  purpose?: string;
  sourceCandidateIds: string[];
  sourceObjectIds: string[];
  evidenceIds: string[];
  confidence: "confirmed" | "inferred" | "unknown";
  unknownFields: string[];
  reviewItems: string[];
}
```

### 11.4 局部校验

输出校验分三层：

1. Transport Schema：JSON 类型、必填字段、枚举和长度。
2. Reference Validation：Candidate、对象和 Evidence ID 是否存在。
3. Completion Gate：高价值 Candidate 是否全部得到处理。

单个 ServiceDraft 引用错误时，只拒绝该项并返回结构化错误：

```ts
interface ItemValidationError {
  itemId: string;
  field: string;
  code: string;
  allowedValues?: string[];
  message: string;
}
```

允许同一次 SDK run 根据错误修复。只有安全边界、候选遗漏或整体输入哈希不匹配时，才拒绝整批结果。

### 11.5 Token 控制

- 每个 Candidate 最多携带 4 个 unit、4 个进程、4 个容器、8 个端口、12 个路径和 12 个 Evidence ID。
- 超出部分使用计数与查询引用表示。
- 相同静态契约不重复拼入长 Prompt，使用短版本号引用。
- Wiki 已生成后不再发送完整 `wiki_source`。
- Token 使用必须区分 input、cached input、output 和 reasoning。

## 12. 受控补探测

### 12.1 Probe 类型

保留并批量化以下结构化请求：

- `systemd_unit_details`
- `process_runtime`
- `process_cgroup`
- `socket_ownership`
- `container_inspect`
- `compose_metadata`
- `path_metadata`
- `directory_listing`
- `config_summary`
- `log_metadata`
- `path_search`

### 12.2 Probe Plan 编译

Codex 返回的是调查意图。编译步骤：

1. Schema 校验。
2. 验证 Candidate、Investigation 和 Evidence 来源。
3. 规范化路径、unit、PID、容器 ID 和搜索词。
4. 计算语义缓存键并删除重复请求。
5. 使用路径 Trie 合并覆盖请求。
6. 按命令类型生成批量 CollectionTask。
7. 执行并产生对象级 ProbeResult。
8. 脱敏、持久化和更新索引。

### 12.3 执行并发

- unit/container/stat 可批量执行。
- 小型独立配置摘要可以最多 4 并发。
- 目录 `find` 默认最多 2 并发。
- 同一祖先路径下的扫描串行或合并，避免重复磁盘压力。
- Probe 总时长达到预算后停止调度新任务，运行中任务正常取消并记录。

### 12.4 信息增益

每个 Probe 完成后计算：

```ts
interface ProbeYield {
  newEvidenceCount: number;
  resolvedFieldCount: number;
  resolvedQuestionCount: number;
  newServiceCount: number;
  changedConfidenceCount: number;
}
```

连续一轮没有解决字段或问题时，默认不自动开启下一轮。

## 13. Deployment Inventory

### 13.1 数据契约

```ts
interface DeploymentInventory {
  inventoryId: string;
  schemaVersion: "3.0";
  sourceScanId: string;
  sourceEvidenceHash: string;
  semanticStatus: "verified" | "partially_verified" | "unverified";
  generatedAt: string;
  host: HostSummary;
  services: DeploymentService[];
  filteredGroups: FilteredEvidenceGroup[];
  exposedPorts: PortAssignment[];
  storageAssignments: StorageAssignment[];
  findings: Finding[];
  unresolvedQuestions: string[];
  coverage: InventoryCoverage;
}
```

### 13.2 服务事实边界

每个字段保留来源类型：

```ts
interface AttributedValue<T> {
  value: T;
  certainty: "confirmed" | "inferred" | "unknown";
  source: "collector" | "correlation" | "codex" | "human";
  evidenceIds: string[];
}
```

AI 不能把 `inferred` 自动升级为 `confirmed`。确认状态只能来自直接采集证据或人工确认。

### 13.3 稳定 ID

- 原始对象 ID 基于对象固有标识和主机作用域。
- Candidate ID 基于排序后的 source object ID 集合。
- Service ID 首选稳定部署标识；否则基于 source object ID 集合。
- Inventory ID 基于 scan ID 和最终内容哈希。

这样可以支持重试幂等、增量刷新和 Wiki Revision 对比。

## 14. Wiki 与报告

### 14.1 构建流程

```text
Deployment Inventory
  -> Local Wiki Skeleton
  -> Codex Wiki Narrative
  -> Narrative Reference Validation
  -> Wiki Projection
  -> Local Quality Gate
  -> HTML / DOCX / Markdown
```

### 14.2 本地生成内容

- 主机事实表。
- 服务名称、状态、部署方式。
- unit、进程、容器、端口和路径表。
- 存储与网络映射。
- 未知项、冲突和 Probe 状态。
- 过滤统计和采集覆盖。

### 14.3 Codex 生成内容

- 执行摘要。
- 服务器定位和部署架构说明。
- 服务用途和服务间的本地资源关系说明。
- 运维关注点、重点风险和人工确认建议。

### 14.4 自动结束

`compose_wiki` 成功后执行本地质量门禁。通过则直接将 Pipeline 标记为 `completed`，不再调用 Codex 生成 `final` 决策。

## 15. 交互式 Agent

### 15.1 定位

Agent 输入是稳定的 Deployment Inventory，而不是未经筛选的完整 Snapshot。它用于报告后的开放式问题，不负责首次发现流程的每个步骤。

### 15.2 Agent 工具

- `read_inventory`
- `read_service`
- `read_evidence`
- `search_resource_index`
- `request_probe_batch`
- `apply_inventory_revision`
- `compose_wiki_revision`
- `review_wiki_revision`

工具优先支持批量参数。一次模型决策允许多个只读工具调用，但投影修改必须在同一个原子 revision 中提交。

### 15.3 Revision

Agent 修改不覆盖原 Inventory：

```text
inventory-v1
  -> revision-1
  -> inventory-v2
  -> wiki-v2
```

每个 Revision 保存变更原因、Evidence ID、Agent Session、Codex Thread 和人工输入。

## 16. CLI 设计

### 16.1 推荐入口

```bash
# 默认：快速扫描、批量语义发现、一次可选补探测、生成 Wiki
opsense inspect --host <host> --user <user> --profile standard

# 最快得到本地部署线索，不等待 Codex
opsense scan --host <host> --user <user> --profile fast

# 对已有扫描执行或重试语义发现
opsense discover --scan <scan-id> --provider codex

# 使用稳定 Inventory 生成或重新生成报告
opsense report --inventory <inventory-id>

# 报告后继续调查
opsense agent --inventory <inventory-id>
```

### 16.2 关键参数

- `--profile fast|standard|deep`
- `--no-ai`
- `--max-ai-calls`
- `--max-session-tokens`
- `--max-session-duration-ms`
- `--max-probes`
- `--max-probe-rounds`
- `--focus <name-or-id>`
- `--resume <run-id>`

默认参数：

| 参数 | 默认值 |
| --- | ---: |
| `profile` | `standard` |
| `maxAiCalls` | 3 |
| `maxSessionTurns` | 12 |
| `maxProbeRounds` | 1 |
| `maxProbes` | 20 |
| `turnTimeoutMs` | 120000 |

移除或废弃 `--max-agent-runs 200` 这种可以反复重置单次预算的设计。

### 16.3 进度输出

进度以固定阶段和工作量显示，不使用“已审查原始 service 百分比”：

```text
Run: scan-...
Stage: discovering
Baseline: completed in 22.4s, 31 SSH commands
Candidates: 14 protected, 168 system objects grouped
AI: 1/3 calls, 82.6k tokens
Probe: 0/1 rounds, 0/20 requests
Inventory: ready, semanticStatus=partially_verified
```

## 17. 持久化与恢复

### 17.1 阶段清单

`run.json` 保存：

```ts
interface PipelineRun {
  runId: string;
  workflowVersion: "v3_pipeline";
  state: PipelineState;
  currentStage: PipelineStage;
  completedStages: Array<{
    stage: PipelineStage;
    sourceHash: string;
    outputHash: string;
    finishedAt: string;
  }>;
  budgets: PipelineBudgets;
  metricsFile: string;
  outputFiles: string[];
  lastError?: StructuredFailure;
}
```

### 17.2 恢复算法

1. 加载 `run.json`。
2. 校验各阶段文件 Schema 和 hash。
3. 找到最后一个有效阶段。
4. 检查目标阶段所需外部能力。
5. 从该阶段继续，不重新执行已完成任务。

如果需要新的 SSH Probe 但没有连接凭据：

- 使用 SSH Agent 或原 identity file 自动重连；或者
- 保存为 `partial` 并明确要求用户重新提供连接信息。

不得声称“离线恢复支持补探测”。

## 19. 安全实现

### 19.1 批量参数安全

批量命令不接受拼接后的字符串，只接受有上限的类型化数组：

```ts
interface BatchParameterSpec {
  kind: "string_array";
  minItems: number;
  maxItems: number;
  itemPattern: RegExp;
  itemMaxLength: number;
}
```

渲染器逐项转义，审计记录使用脱敏后的逻辑参数摘要。

### 19.2 配置摘要

配置文件默认只提取：

- 顶层 section/key 名。
- 监听地址和端口等非敏感结构化值。
- 路径引用。
- 敏感字段存在性，不保存值。

密码、Token、Secret、私钥、Cookie、Authorization、连接串凭据和环境变量值不得进入持久化层或 Codex 输入。

### 19.3 最小权限

- 默认非 root 扫描。
- 只有明确允许的 command spec 可以使用 sudo。
- sudo 密码只存在于进程内存，通过 stdin 发送。
- Docker 权限不足时标记覆盖缺口，不尝试修改用户组或 daemon 权限。

## 20. 测试方案

### 20.1 单元测试

- Scheduler 优先级、依赖、缓存、取消和自适应并发。
- systemd/Docker/stat 批量参数验证和解析。
- 路径 Trie 覆盖、文件/目录区分和禁止路径阻断。
- Resource Graph 节点、边和连通分量。
- 高价值候选保护和普通系统聚合。
- Batch Discovery 局部校验和完整度门禁。
- Probe 去重、预算和信息增益。
- Inventory/Wiki 的 Evidence 引用校验。

### 20.2 集成测试

建立至少以下 fixture：

1. 300 个普通 systemd unit，只有 5 个高价值部署服务。
2. 100 个 Docker 容器和多个 Compose 项目。
3. Nginx、Java 应用、PostgreSQL、Redis、MinIO 混合部署。
4. 非标准 Go/Rust 程序和 `/data/custom-app` 路径。
5. Docker overlay、veth、临时 mount 和伪文件系统噪声。
6. SSH 高延迟、命令缺失、权限不足、超时和输出截断。
7. Codex 无效引用、部分 Item 错误、超时和不可用。

### 20.3 性能测试

性能测试必须断言：

- 300 个 unit 不产生 300 次 `systemctl show`。
- 100 个容器不产生 100 次 `docker inspect`。
- 200 个相关路径不产生 200 个初始 `find`。
- standard profile 的基础 SSH 命令数不超过目标阈值。
- 正常 AI 流程不超过 3 次调用。
- 工具局部校验失败不会产生新的完整发现回合。
- Wiki 完成后不会再执行 final 模型调用。

### 20.4 真实服务器验收

- Debian/Ubuntu。
- RHEL/Rocky。
- Alpine 或非 systemd 主机。
- Docker/Compose 密集主机。
- 非标准自研服务主机。
- 无 Docker 权限的最小权限账户。

每个样本保存脱敏后的指标，不保存真实敏感配置和主机身份。

## 21. 全新主线实施方案

### 21.1 第一阶段：建立 v3.0 骨架与领域契约

- 定义 PipelineRun、RawEvidence、ResourceGraph、DeploymentCandidate、DeploymentInventory 和 WikiProjection。
- 建立新的 v3.0 工作区布局和 Schema，不读取旧工作区。
- 新建 `InspectWorkflow` 和阶段状态机。
- 建立 `metrics.json`、阶段耗时和全局预算契约。
- 将仍有价值的解析器测试迁入 v3.0 契约测试。

旧 Projection、旧 Agent 完成门禁和旧 CLI 编排不进入新骨架。

### 21.2 第二阶段：重写采集运行时

- 引入共享 Collection Scheduler。
- 实现批量 systemd show、Docker inspect 和 stat。
- 实现运行内语义缓存、统一并发和指标。
- 复用符合新接口的 SSH transport、命令安全与解析代码。
- 删除 M3/M4/M5 固定串行编排和初始全量目录读取。

### 21.3 第三阶段：实现快速发现

- 实现 `fast`、`standard`、`deep` profile。
- 建立 Resource Graph 和确定性关联规则。
- 实现高价值 Candidate 保护与系统对象聚合。
- 在 `inventory_ready` 阶段输出本地 Deployment Inventory。

### 21.4 第四阶段：实现批量 AI Discovery

- 实现 `BatchDiscoveryDecision` 和单次候选提交。
- 支持逐项引用校验、局部错误和 SDK 内修复。
- 实现 Discovery Completion Gate。
- 首次发现链路不引入旧单工具 Agent loop。

### 21.5 第五阶段：实现 Probe、Wiki 与报告

- 实现 Probe Plan 去重、路径合并和一次批量执行。
- 实现可选 Reconciliation 调用。
- 从稳定 Deployment Inventory 构建 Wiki Projection。
- `compose_wiki` 后由本地质量门禁自动完成。
- HTML、DOCX、Markdown 只消费 v3.0 Wiki Projection。

### 21.6 第六阶段：实现报告后 Agent 并删除旧主线

- Agent 只读取 v3.0 Deployment Inventory 和 Evidence Store。
- 实现 Inventory Revision 与 Wiki Revision。
- 直接删除旧 `--max-agent-runs`、旧首次扫描 Agent 工作流和旧 Projection 代码。
- 删除仅服务于旧 Schema、旧 Session 和旧报告产物的测试与兼容分支。

以上阶段建议在独立 v3.0 开发分支完成。项目不要求中间提交继续运行旧工作流，但每个阶段必须保持 v3.0 已完成部分的类型检查和测试通过。

## 24. 风险与应对

| 风险 | 应对 |
| --- | --- |
| 快速扫描减少目录读取后漏掉非标准服务 | 保护未知监听进程和自定义路径；standard profile 允许一次补探测 |
| 批量命令在不同发行版兼容性不一致 | 保留小批次和安全降级；失败时二分定位，不默认全部逐项执行 |
| 本地聚合错误合并不同服务 | 只有强关联边自动合并，弱关联交给 Codex；保留原始对象和边证据 |
| AI 批量结果遗漏候选 | 本地 Completion Gate 强制覆盖所有受保护 Candidate |
| AI 部分输出错误导致整批重试 | 逐项校验、合法项保留、同一次 SDK run 内修复非法项 |
| Codex 不可用 | 输出 `unverified` 本地 Inventory，不生成伪 AI Wiki |
| Probe 给目标服务器造成负载 | 目录低并发、全局时长与条目预算、默认一轮、显式 deep profile |
| 开发工作区残留旧格式导致误读 | v3.0 使用新格式标识；遇到旧格式直接失败并提示清理，不提供兼容读取 |

## 25. v3.0 Definition of Done

- `fast` profile 在目标样本上 P95 一分钟内生成本地 Evidence Inventory。
- 300 个 systemd unit 的详情查询按批次执行，不出现逐 unit N+1。
- 100 个容器的 inspect 按批次执行，不出现逐容器 N+1。
- 初始扫描不递归扫描所有路径或读取所有配置文件。
- 本地 Resource Graph 能关联 unit、PID、socket、容器、Compose、mount 和路径。
- 所有高价值 Candidate 均被保护，普通系统对象可以聚合。
- standard profile 正常只调用 2～3 次 Codex，默认最多一轮 Probe。
- 业务校验支持局部错误，不因单项错误重跑完整发现。
- Wiki 成功后由本地门禁完成流程，不执行额外 final 模型调用。
- Codex 不可用时仍产生明确标记为 `unverified` 的本地部署清单。
- Agent 可以从稳定 Inventory 发起后续调查并生成 Revision。
- 仓库不包含旧 Snapshot、Projection、Session 或 CLI 的兼容与迁移分支。
- 自动化测试、真实样本和 `metrics.json` 证明性能目标与安全边界成立。
