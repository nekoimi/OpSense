# OpSense 技术方案文档 v1.0

## 1. 文档目的

本文档根据《需求初稿 v1.0》给出 OpSense 第一版的可实施技术方案，包括本地 CLI 架构、SSH 扫描流程、数据模型、AI/Codex 接入方式、安全边界、代码结构、实施阶段和验收标准。

OpSense 面向一台陌生的 Linux 服务器，通过只读方式采集系统、存储、网络和部署服务信息，形成结构化服务器快照，再由规则引擎和 AI 整理成便于查看、交接和后续维护的服务器文档。

---

## 2. 建设目标与边界

### 2.1 建设目标

系统需要完成以下闭环：

1. 通过 SSH 连接目标 Linux 服务器。
2. 获取操作系统、硬件、网络、磁盘、分区、挂载点和目录概况。
3. 探测 systemd、进程、端口、Docker/Compose 及常见基础服务。
4. 根据运行态线索定向定位部署目录、配置、日志和数据位置。
5. 将原始证据归一化为统一的服务器与服务清单。
6. 对敏感数据进行本地过滤和脱敏。
7. 调用 Codex 或其他 AI Provider 进行解释、归纳和风险提示。
8. 生成 Word（`.docx`）服务器报告和静态 HTML 报告，并可输出 Markdown 调试文件。

第一版以纯本地 CLI 工具交付，不建设 Web 管理后台、HTTP API、任务队列、用户系统或中心化服务。扫描快照、AI 分析结果和报告全部保存在用户本机。

### 2.2 第一版交付范围

第一版以一个可以在用户本机直接运行的 CLI 为最终交付物，最小闭环为：

```bash
opsense inspect --host server.example.com --user ops --provider codex
```

该命令需要完成：

1. 连接一台 Linux 服务器。
2. 执行系统、磁盘、网络、systemd、进程、端口和 Docker 探测。
3. 根据已发现路径执行受限目录扫描。
4. 在本地生成脱敏后的 `snapshot.json`。
5. 调用 Codex 生成结构化分析结果。
6. 在本地输出 Word（`.docx`）和静态 HTML 报告，并保留 Markdown 调试输出。

首版一次只处理一台服务器，不包含批量主机、账号体系、任务调度和远程报告托管。

### 2.3 第一阶段不做

* 不建立完整的服务依赖图。
* 不还原复杂业务调用链。
* 不自动修改服务器配置。
* 不自动执行启停、升级、备份或故障修复。
* 不要求发现跨服务器、云平台或外部 SaaS 资源。
* 不承诺识别所有非标准自定义应用。
* 不允许 AI 直接登录目标服务器并自由执行命令。

### 2.4 核心原则

* **事实优先**：系统命令、运行状态和配置文件是事实来源。
* **AI 后置**：先完成确定性采集和归并，再调用 AI。
* **线索驱动**：先读取运行态入口，再定向扫描目录，不遍历整台服务器。
* **默认只读**：采集命令必须来自允许列表，禁止修改系统状态。
* **最小采集**：只读取完成服务识别所需的信息。
* **证据可追溯**：重要结论必须关联采集命令、文件位置或原始字段。
* **结果可复现**：同一份快照在不调用 AI 时也能生成基础报告。

## 3. 总体架构

```text
                          本地 OpSense CLI
+----------------+    +----------------------+    +------------------+
| CLI Command    | -> | Scan Orchestrator    | -> | Local Snapshot   |
+----------------+    +----------+-----------+    +--------+---------+
                              |                         |
                              | SSH                     |
                              v                         v
                    +-------------------+      +---------------------+
                    | SSH Executor      |      | Normalize / Merge   |
                    | 只读命令模板       |      | Evidence Engine     |
                    +---------+---------+      +----------+----------+
                              |                           |
                              v                           v
                       目标 Linux 服务器          +---------------------+
                                                  | Redaction Layer     |
                                                  +----------+----------+
                                                             |
                                          +------------------+------------------+
                                          |                                     |
                                          v                                     v
                               +---------------------+              +---------------------+
                               | Codex AI Provider   |              | Basic Report Engine |
                               | 读取脱敏快照工作区   |              | 无 AI 也可运行       |
                               +----------+----------+              +----------+----------+
                                          |                                     |
                                          +------------------+------------------+
                                                             v
                                                  +---------------------+
                                                  | DOCX / Markdown     |
                                                  +---------------------+
```

### 3.1 本地运行形态

第一版采用纯本地、无 Agent 模式：

1. 用户在自己的电脑或运维工作机运行 OpSense CLI。
2. 本地 CLI 通过 SSH 执行预定义的只读命令模板。
3. 目标服务器返回命令输出和文件元数据，不安装或上传 OpSense 程序。
4. 本地 CLI 将输出解析成结构化快照，并完成归并和脱敏。
5. 本地调用 Codex，并生成 Word 和静态 HTML 报告及可选的 Markdown 调试文件。

本地目录建议如下：

```text
~/.opsense/
|-- config.json
|-- runs/<scan-id>/
`-- reports/<host>/<scan-time>/
```

第一版不运行本地守护进程或后台服务，也不向目标服务器上传二进制文件，不要求目标服务器安装 Node.js、Python 或其他额外运行时。

## 4. 技术选型

### 4.1 推荐技术栈

| 模块 | 推荐技术 | 选择原因 |
| --- | --- | --- |
| 本地 CLI | TypeScript + Node.js | 便于接入 Codex TypeScript SDK、编排 SSH 扫描和生成报告 |
| SSH 执行 | OpenSSH 或 TypeScript SSH 库 | 在本机执行固定命令模板，不要求目标服务器安装 Agent |
| 本地存储 | JSON 文件 + 目录 | 首版无需数据库，快照、证据和报告直接按 scan ID 保存 |
| 数据交换 | JSON / JSON Lines | 易调试，便于采集、归并、报告和 AI 模块交换数据 |
| 配置解析 | 专用解析器 | systemd、JSON、YAML、INI 等优先使用结构化解析 |
| 文档输出 | Word（`.docx`）+ HTML + Markdown | Word 用于正式交付，HTML 用于离线浏览，Markdown 用于调试和版本管理 |
| AI 接入 | Provider 接口 + Codex SDK | Codex 作为首选，同时保留替换其他模型的能力 |

### 4.2 首版依赖建议

| 用途 | 建议依赖 |
| --- | --- |
| CLI 参数与子命令 | `commander` |
| SSH 连接与命令执行 | `ssh2` |
| JSON Schema 校验 | `ajv` |
| YAML 解析 | `yaml` |
| INI/systemd 辅助解析 | `ini` 或项目内专用解析器 |
| Markdown 渲染 | `marked` |
| HTML 模板 | `handlebars` |
| Word 文档生成 | `docx` |
| Codex | `@openai/codex-sdk` |
| 测试 | `vitest` |

推荐使用 Node.js 22 或更高版本、TypeScript 5.x 和 pnpm workspace，新项目优先采用当前 LTS。Codex SDK 官方最低要求为 Node.js 18；项目自身采用更高的最低版本可以减少兼容性分支。

### 4.3 不建议第一阶段引入

* 图数据库：当前不做严格依赖图。
* SQLite：首版使用 JSON 文件即可，需要大量历史快照查询时再引入。
* Kubernetes：会显著扩大资源模型和权限边界。
* 全量文件内容索引：成本和敏感信息风险过高。
* 向量数据库：第一阶段文档生成不需要语义检索基础设施。

## 5. 扫描流程设计

扫描不是先执行完整目录 `tree`，而是采用分阶段、线索驱动的探测方式。

```text
SSH 预检
  -> 系统与存储快照
  -> 运行态服务入口
  -> 提取路径线索
  -> 定向目录扫描
  -> 配置解析
  -> 服务归并
  -> 脱敏
  -> AI 分类与补探测计划
  -> 可选的一轮受控补探测
  -> 重新归一化与脱敏
  -> AI 最终分析
  -> 报告投影与生成
```

### 5.1 阶段 A：连接与权限预检

采集内容：

* SSH 连通性和主机指纹。
* 当前用户、UID、用户组。
* 是否可以无交互使用 `sudo -n`。
* 目标 CPU 架构和操作系统。
* 必需命令是否存在。
* 可读取的信息范围。

扫描结果需要标记权限级别：

```text
unprivileged       普通用户扫描
partial_privileged 部分命令可通过 sudo 执行
privileged         可以执行允许列表中的特权只读命令
```

权限不足不应导致整个扫描失败，而应在对应字段标记 `permission_denied`。

### 5.2 阶段 B：系统与存储快照

优先使用支持 JSON 输出的系统命令：

| 类别 | 主要来源 |
| --- | --- |
| OS | `/etc/os-release`、`uname`、`hostnamectl` |
| CPU | `lscpu -J`、`/proc/cpuinfo` |
| 内存 | `/proc/meminfo`、`free -b` |
| 磁盘 | `lsblk -J -b -O` |
| 挂载 | `findmnt -J`、`/etc/fstab` |
| 空间 | `df -B1`、`df -i` |
| 网络 | `ip -j addr`、`ip -j route` |
| DNS | `/etc/resolv.conf`、systemd-resolved 状态 |
| 防火墙 | `nft -j list ruleset`、`iptables-save`、`firewall-cmd`、`ufw status` |
| 软件包 | `dpkg-query`、`rpm`、`apk` |

#### 5.2.1 发行版适配与命令降级

系统采集不直接把字段绑定到单条命令，而是使用逻辑探针。扫描先读取 `/etc/os-release`，归类为 `debian`、`rhel`、`alpine` 或 `unknown`，再按发行版顺序执行预定义命令变体。

```ts
interface ProbeSpec<T> {
  id: string;
  required: boolean;
  variants: ProbeVariant<T>[];
}

interface ProbeVariant<T> {
  commandId: string;
  distributions: DistributionFamily[];
  acceptedExitCodes?: number[];
  parse(result: CommandExecutionResult): T;
}
```

命令缺失、选项不支持、权限不足或解析失败时，探针按顺序尝试下一变体。每次尝试独立保留 evidence；只有必需探针的全部变体失败才生成一个 unknown，可选替代来源失败不影响扫描终态。所有变体必须注册在 SSH 静态只读允许列表中，不允许动态拼接 `sh -c`。

首批降级链覆盖 CPU、`lsblk`、挂载、`df`、Swap、网络地址、路由、时区、虚拟化、防火墙和包管理器。探针之间受 SSH 并发上限约束，单个探针内部顺序执行，防止降级尝试再次造成远端 channel 耗尽。

目录概况只采集关键挂载点下第一层目录的大小、属主和权限，不在此阶段递归读取全部文件。

### 5.3 阶段 C：运行态服务入口

#### systemd

采集：

* 所有 service unit 的加载、启用和运行状态。
* `ExecStart`、`ExecReload`、`WorkingDirectory`。
* `EnvironmentFile`、`User`、`Group`。
* unit 文件实际路径。
* MainPID 和最近启动时间。

#### 进程

采集：

* PID、PPID、UID、启动时间、命令行。
* `/proc/<pid>/exe`。
* `/proc/<pid>/cwd`。
* cgroup 和容器归属。
* 进程监听的端口。

默认不采集完整 `/proc/<pid>/environ`。如确有需要，只允许提取环境变量键名，并在目标服务器本地完成脱敏。

#### 端口

通过 `ss -lntup` 或 Netlink 获取：

* 协议、监听地址和端口。
* 关联 PID 和进程名称。
* IPv4 / IPv6。
* 仅本地监听或对外监听。

#### Docker / Compose

采集：

* Docker 版本和运行状态。
* 容器 ID、名称、镜像、状态和启动时间。
* 端口映射、网络、Volume、Bind Mount。
* RestartPolicy、Healthcheck。
* Compose project、service、working directory 标签。
* 环境变量键名，默认不保存敏感值。

#### 常见入口

在已安装或正在运行时再执行对应探测：

* Nginx：配置入口和 `nginx -T`。
* Caddy：Caddyfile 或适配后的 JSON 配置。
* MySQL / PostgreSQL / Redis：进程、端口、配置入口和数据目录。
* cron / systemd timer：可能用于启动、部署和备份的定时任务。
* Supervisor：受管进程及配置路径。

### 5.4 阶段 D：构建路径种子

从运行态信息中提取需要进一步扫描的路径：

* systemd `WorkingDirectory`。
* systemd `ExecStart` 可执行文件和脚本目录。
* systemd `EnvironmentFile`。
* 进程 `exe` 和 `cwd`。
* 命令行参数中的绝对配置路径。
* Docker Bind Mount 和 Volume Mountpoint。
* Compose working directory。
* Nginx/Caddy include 和静态文件目录。
* 数据库配置中明确声明的数据和日志目录。

每个路径种子需要保存来源，例如：

```json
{
  "path": "/opt/order-api",
  "sourceType": "systemd.working_directory",
  "sourceId": "order-api.service",
  "confidence": "confirmed"
}
```

### 5.5 阶段 E：受限目录扫描

扫描器对路径种子和常见部署根目录执行受限扫描：

* 默认最大深度：4。
* 单目录默认最大文件数：5000。
* 单文件元数据读取超时。
* 默认不跨文件系统边界。
* 默认只读取文件名、大小、权限、属主、修改时间和类型。
* 只有配置识别器命中的小文件才允许读取内容。
* 大文件只记录元数据和可选哈希，不读取内容。

默认排除：

```text
/proc
/sys
/dev
/run
/tmp
.git
node_modules
vendor
cache
数据库表空间
容器 overlay 存储层
```

常见部署根目录 `/opt`、`/srv`、`/var/www`、`/data`、`/app` 和用户目录只进行浅层候选发现，命中以下特征后才进入深层扫描：

```text
docker-compose.yml
compose.yml
Dockerfile
package.json
pyproject.toml
requirements.txt
go.mod
pom.xml
*.service
start*.sh
deploy*.sh
nginx.conf
Caddyfile
```

### 5.6 阶段 F：配置解析

解析优先级：

1. 标准命令的 JSON 输出。
2. 标准格式解析器，如 JSON、YAML、INI、XML、TOML。
3. 特定服务配置解析器。
4. 受限的文本规则。
5. AI 辅助理解。

AI 不应替代 systemd、Compose、Docker inspect 等确定性解析。

### 5.7 阶段 G：服务归并

同一服务可能同时出现在 systemd、进程、端口和目录扫描结果中，需要归并成一个 `ServiceRecord`。

主要归并依据：

1. systemd MainPID 与进程 PID 一致。
2. 进程 cgroup 指向对应 systemd unit 或容器。
3. 可执行文件、工作目录或容器 ID 一致。
4. Docker Compose project/service 标签一致。
5. 端口记录关联相同 PID。

归并规则只处理直接归属，不推断业务上下游依赖。

M6 使用确定性并查集构建服务归属组，节点包括 systemd unit、进程、容器和 Compose service。归并边只允许来自 MainPID、完整 cgroup、容器 InitPID、父子进程树、Compose 标签以及 Socket 的 PID/容器 ID；工作目录和可执行路径只用于把 Artifact 关联到服务，不允许仅凭路径把两个服务合并。共享路径同时匹配多个服务时不强制归属，避免把同一项目目录中的配置和日志复制到所有服务。

服务 ID 按 Compose project/service、容器名称、systemd unit 或独立进程运行签名生成，不依赖输入顺序。派生 Evidence 使用 `sourceEvidenceIds` 回溯原始命令或文件证据，并记录 normalizer 版本。确定性运行态实体标记为 `confirmed`，仅通过独立进程规则形成的服务标记为 `inferred`；状态、自启动或身份来源不一致时通过 `conflictFields` 和 `confidence=conflict` 保存，缺失字段继续写入 `unknownFields`。

进程采集为 cgroup 列预留固定宽度，避免 `ps` 默认截断容器 ID 或 `.service` 名称。若旧系统无法提供完整 cgroup，可在已确认的 systemd MainPID 或容器 InitPID 范围内沿父子进程树补充归属，但不会跨越另一个已确认的服务入口。

## 6. 数据模型

### 6.1 核心实体

```text
ScanSession
  |-- HostSnapshot
  |-- StorageSnapshot
  |-- NetworkSnapshot
  |-- ProcessRecord[]
  |-- SocketRecord[]
  |-- ContainerRecord[]
  |-- PathSeedRecord[]
  |-- ServiceRecord[]
  |-- ArtifactRecord[]
  |-- EvidenceRecord[]
  |-- FindingRecord[]
  `-- AiAnalysis
```

### 6.2 ServiceRecord 示例

```json
{
  "id": "svc_order_api",
  "name": "order-api",
  "displayName": "Order API",
  "deploymentType": "systemd",
  "status": "running",
  "enabledAtBoot": true,
  "processIds": [2341],
  "listenSockets": ["0.0.0.0:8080"],
  "deployDirectories": ["/opt/order-api"],
  "configFiles": ["/opt/order-api/config/app.yml"],
  "environmentFiles": ["/opt/order-api/.env"],
  "logLocations": ["journalctl -u order-api"],
  "dataDirectories": ["/data/order-api"],
  "startCommand": "systemctl start order-api",
  "stopCommand": "systemctl stop order-api",
  "restartCommand": "systemctl restart order-api",
  "evidenceIds": ["ev_1001", "ev_1002"],
  "confidence": "confirmed",
  "unknownFields": ["purpose"]
}
```

### 6.3 EvidenceRecord 示例

```json
{
  "id": "ev_1001",
  "kind": "command_output",
  "source": "systemctl show order-api.service",
  "field": "WorkingDirectory",
  "value": "/opt/order-api",
  "collectedAt": "2026-08-14T02:00:00Z",
  "opsenseVersion": "0.1.0",
  "status": "success",
  "sensitivity": "internal"
}
```

### 6.4 确定程度

```text
confirmed  系统命令、配置或运行状态直接确认
inferred   根据多个事实规则推断
unknown    当前无法确认
conflict   不同证据之间存在冲突
```

AI 不允许把 `inferred` 或 `unknown` 自动改成 `confirmed`。

## 7. AI 与 Codex 接入设计

### 7.1 当前问题与 M9 目标

基础扫描需要尽量保留事实，因此 M4-M6 会采集和归并大量 systemd unit、进程和容器候选。真实测试快照中，288 个服务候选包含 227 个 systemd 服务，其中 125 个处于停止状态，220 个没有监听端口，210 个没有部署目录。如果报告直接展开全部候选，会把操作系统自身服务和实际部署应用混在一起。

M9 不再只负责“给现有服务写摘要”，而是新增三个核心能力：

1. 对服务候选进行语义分类和报告相关性判断。
2. 对固定规则无法覆盖的目录、配置和服务类型进行语义关联。
3. 在严格安全预算内提出结构化补探测请求，补充证据后再生成最终分析。

原始 `snapshot.json` 始终保留完整候选。Codex 只生成独立解释层和报告投影建议，不能删除候选或改写运行状态、端口、路径、部署方式等事实。

### 7.2 混合判断原则

服务筛选采用“确定性事实 + 基线分类器 + Codex 语义判断 + 治理规则”的混合模型：

* 确定性采集器负责 systemd、进程、端口、容器、镜像、挂载、目录和配置事实。
* `BaselineRelevanceClassifier` 根据端口、自定义路径、容器、运行状态和 unit 来源提供无 AI 时的保守分类。
* Codex 结合名称、描述、ExecStart、镜像、Compose 项目、路径和配置线索识别服务角色及用途。
* 治理层覆盖不安全或不合理的 AI 结果，例如禁止隐藏失败服务、外部监听服务和明显自定义部署。
* 报告层消费分类结果，但完整候选清单仍保留在快照和机器可读索引中。

不维护覆盖所有发行版和软件名称的巨型排除名单。固定规则只处理高确定度特征，Doris、Hadoop、MinIO 和企业自研应用等非标准候选主要由证据特征和 Codex 语义判断补充。

### 7.3 两阶段分析与补探测流程

M9 将单次 AI 调用调整为最多两阶段、一次补探测的闭环：

```text
基线快照
  -> 确定性服务归并与脱敏
  -> 生成紧凑 AI 候选视图
  -> Codex 阶段 1：服务分类、路径分类、ProbeRequest
  -> 本地 Schema 与 ProbePolicy 校验
  -> 可选的一轮只读补探测
  -> 证据入库、重新归一化与脱敏
  -> Codex 阶段 2：最终摘要、用途、风险和未知项
  -> 报告投影
```

如果 Codex、补探测或第二阶段失败，流程使用基线分类器和已有快照继续生成报告，不回滚已经完成的事实采集。

### 7.4 Provider 与 Codex SDK

业务层只依赖统一接口：

```ts
export interface AiProvider {
  readonly name: string;

  analyze(input: AnalysisInput, options?: AnalysisOptions): Promise<AnalysisResult>;
}
```

首批实现：

```text
CodexProvider       使用本地 Codex SDK 执行两阶段语义分析
NoopProvider        返回合法空解释层，使用基线分类器生成报告投影
OpenAIProvider      Later，可通过 OpenAI API 接入其他结构化模型
```

根据官方 OpenAI Docs，`@openai/codex-sdk` 可以在 Node.js 服务端启动、继续和恢复本地 Codex thread，适合嵌入内部工具。TypeScript SDK 最低要求为 Node.js 18，OpSense 继续使用项目当前更高的 Node.js 基线。

```ts
import { Codex } from "@openai/codex-sdk";

const codex = new Codex();
const thread = codex.startThread();
const planResult = await thread.run(classificationPrompt);
const finalResult = await thread.run(finalAnalysisPrompt);
```

每个 scan 默认创建一个 thread。thread ID、Provider、模型、开始结束时间、重试次数、超时和最终状态写入 `ai-run.json`。Codex 运行在用户本机，不运行在目标 Linux 服务器上，也不能直接获得 SSH 执行器对象。

### 7.5 脱敏 AI 工作区

每次分析创建独立工作区：

```text
~/.opsense/runs/<scan-id>/ai-input/
|-- context.md
|-- host.json
|-- storage.json
|-- network.json
|-- service-candidates.json
|-- path-candidates.json
|-- findings.json
|-- evidence-index.json
|-- redaction-report.json
|-- classification-schema.json
|-- probe-plan-schema.json
`-- analysis-schema.json
```

`service-candidates.json` 是面向语义判断的紧凑视图，不复制全部证据正文。每个候选至少包含：

* 服务 ID、名称、描述、状态和部署方式。
* systemd fragment、ExecStart、WorkingDirectory 和 unit 来源。
* 进程名、命令摘要、cgroup、监听端口和暴露范围。
* 容器、镜像、Compose 项目、标签和挂载。
* 已发现的部署、配置、日志、数据和环境文件路径。
* 关联 Evidence ID 和仍缺失的字段。

`evidence-index.json` 只提供证据类型、来源、状态和摘要定位。Codex 默认不能读取 SSH 密钥、本地 OpSense 配置、原始 `.env`、未脱敏命令输出或报告目录以外的本地文件。运行时应将 Codex 的工作目录限制到 `ai-input/`，并使用可用的只读沙箱配置。

### 7.6 服务语义输出契约

第一阶段输出 `ai-plan.json`，核心结构如下：

```json
{
  "serviceAssessments": [
    {
      "serviceId": "service:compose:minio:minio",
      "role": "infrastructure",
      "reportPlacement": "supporting",
      "purpose": "对象存储服务",
      "reason": "容器镜像、9000 端口和数据挂载共同指向 MinIO",
      "confidence": "inferred",
      "evidenceIds": ["evidence:docker.inspect:minio"]
    }
  ],
  "pathAssessments": [],
  "probeRequests": []
}
```

`role` 取值：

* `application`：业务应用或企业自研服务。
* `middleware`：消息、缓存、注册中心、任务调度等中间件。
* `infrastructure`：数据库、对象存储、反向代理、容器平台等基础组件。
* `system`：操作系统启动、设备、会话、包管理和维护服务。
* `unknown`：当前证据不足。

`reportPlacement` 取值：

* `primary`：主要部署服务，生成完整详情。
* `supporting`：支撑组件，生成完整或简化详情。
* `system_summary`：进入系统服务概况，不逐条生成详情。
* `needs_review`：进入待确认候选，展示缺失证据。

每条分类必须包含原因、确定程度和 Evidence ID。AI 不得修改服务事实字段，也不能把 `inferred` 或 `unknown` 提升为 `confirmed`。

治理层至少执行以下覆盖规则：

* `failed` 的服务必须出现在报告异常项或待确认项中。
* 存在外部监听端口的服务不能只进入普通系统服务统计。
* Compose、Docker、自定义 `/etc/systemd/system` unit，以及使用 `/opt`、`/srv`、`/data`、用户目录或非系统可执行路径的服务，不能在没有明确证据时归为普通系统噪声。
* 没有端口、没有运行进程、没有自定义路径且来源于系统 unit 目录的普通 unit，可以进入 `system_summary`。

### 7.7 路径语义和 ProbeRequest

Codex 可以对路径候选附加以下语义：

```text
deploy | config | data | log | backup | runtime | system | unknown
```

固定规则无法确认路径用途时，Codex 可以提出结构化 `ProbeRequest`：

```json
{
  "kind": "directory_listing",
  "path": "/opt/doris",
  "serviceIds": ["service:process:abc123"],
  "sourceEvidenceIds": ["evidence:processes"],
  "reason": "进程可执行文件位于该目录，需要确认配置和数据子目录",
  "expectedFields": ["configFiles", "dataDirectories"],
  "maxDepth": 2
}
```

第一版只允许四类请求：

* `directory_metadata`：读取目录自身元数据和容量概况。
* `directory_listing`：按深度和文件数限制列出候选项。
* `config_summary`：使用现有结构化解析器读取受限配置摘要。
* `path_search`：在批准的部署根和已知数据挂载中，按受限名称词搜索候选目录或文件。

`path_search` 的搜索词必须来自已采集的服务名、进程可执行名、systemd unit、容器镜像或 Compose 标签，不能接受自由正则表达式或任意 glob。搜索根只能来自配置批准的部署根以及快照中确认的数据挂载，必须限制最大深度和最大命中数。

Codex 不能返回 Shell 命令。`ProbePlanValidator` 必须确认路径或搜索词可由现有证据派生、目标不属于禁止目录，并限制请求数、深度、文件数、命中数、总字节数和超时。通过校验的请求由现有安全命令目录编译执行；拒绝、跳过和失败项写入 `ai-probe-audit.json`。

第一版最多执行一轮补探测，默认不跨挂载点，不扫描 `/`，并继续排除 `/proc`、`/sys`、`/dev`、`/run` 和容器 overlay 存储层。

### 7.8 报告投影

报告不直接遍历 `snapshot.services` 生成全部详情，而是使用基线分类与 AI 分类合并后的 `ServiceReportProjection`：

```text
主要部署服务
支撑组件
系统服务概况
待确认服务
完整候选索引
```

主要部署服务、支撑组件和待确认服务可以生成详情。系统服务概况只显示总数、运行数、失败数、对外监听数和需要关注的 unit。完整候选索引保留所有服务 ID、名称、状态、分类和 Evidence，保证报告降噪不会造成事实丢失。

执行摘要必须分别显示候选总数、主要部署服务数、支撑组件数、系统服务数和待确认数。现有单一 `serviceCount` 需要在 M9 演进为分类计数，避免把系统候选总数误解为实际部署服务数量。

Word 和 HTML 使用同一份报告投影。AI 分类、用途和风险必须明确标记为 AI 解释层；确定性端口、状态和路径继续来自快照事实层。

### 7.9 提示词、校验和重试

第一阶段提示词要求 Codex 完成服务分类、路径分类和 ProbeRequest；第二阶段仅在新证据完成归一化和脱敏后生成最终摘要。两个阶段都必须遵守：

```text
1. 只能依据 ai-input 中的脱敏事实。
2. 不得修改服务 ID、状态、端口、路径或部署方式。
3. 每条重要判断必须引用 Evidence ID。
4. 不得把 inferred 或 unknown 写成 confirmed。
5. 不得补写密码、连接信息、业务依赖或未证实的运维流程。
6. 不得输出 Shell 命令或要求绕过 ProbePolicy。
7. 输出必须符合当前阶段的 JSON Schema。
8. 无法确认时使用 unknown 或 needs_review。
```

`finalResponse` 先经过 JSON 解析，再使用 AJV 校验。解析失败、Schema 错误、未知服务 ID、未知 Evidence ID 和越权 ProbeRequest 都视为无效输出。最多进行两次修复重试，重试提示只包含校验错误和允许的契约，不放宽安全边界。

### 7.10 降级与评测

Codex 不可用时，`BaselineRelevanceClassifier` 仍应进行保守降噪，基础 Word 和 HTML 报告必须可生成。基线分类不追求识别所有非标准服务，证据不足的候选进入 `needs_review`，不能静默隐藏。

M9 需要建立跨发行版评测集，至少覆盖 Ubuntu、Debian、Rocky/RHEL 和无 systemd 环境，并包含：

* systemd 启动、会话、设备、包管理和维护服务降噪。
* Nginx、MySQL、PostgreSQL、Redis、Docker 和 Compose 组件。
* Doris、Hadoop、MinIO 等非标准基础服务。
* 使用自定义 unit、非标准路径和企业命名的应用。
* 失败服务、外部监听服务和证据不足服务。

评测指标至少包含主要服务召回率、系统服务误报率、`needs_review` 比例、ProbeRequest 接受率，以及关键服务被错误降级的数量。安全验收要求任意非法 AI 输出都不能触发任意命令、越界目录读取或快照改写。

完成基础闭环后，可以继续使用同一 thread 支持用户追问、快照对比和报告审校。如果未来 Codex 只是更大智能体系统中的一个专业节点，再评估 Codex CLI MCP server；这不是第一版本的必要依赖。

## 8. 脱敏与安全设计

### 8.1 敏感信息分类

```text
public       操作系统版本、状态、端口等低风险信息
internal     服务名称、采集状态和一般运行元数据
sensitive    用户名、主机名、内网地址、路径和命令
secret       密码、Token、私钥、Cookie、云凭据
```

### 8.2 默认脱敏规则

* `.env` 默认只记录变量名，不记录值。
* 私钥文件只记录路径、权限和指纹，不读取正文。
* 数据库连接串隐藏用户名、密码和查询参数。
* URL 中的凭据、Token 和签名参数替换为 `[REDACTED]`。
* Docker 环境变量按敏感键名和值模式双重过滤。
* 命令行中的 `--password`、`--token`、`--secret` 等参数脱敏。
* 远程命令只输出必要字段；结果在本地持久化和发送给 AI 之前再次脱敏。

脱敏在四个输出边界执行：`snapshot.json` 落盘、`audit.jsonl` 追加、AI 输入工作区写入和报告 ViewModel 写入。AI 输入固定执行两遍脱敏，其余边界执行一遍；每次脱敏后都运行残留 secret 扫描，仍有命中时中止对应输出，不允许带病落盘。

每次扫描额外写入 `redaction-report.json`，并在快照中保存同一份摘要。摘要包含脱敏规则版本、执行模式、扫描遍数、各规则命中计数、敏感级别计数和残留扫描结果。报告只记录规则与数量，不记录被替换的原值。

### 8.3 命令安全

本地 SSH 采集模块采用静态命令允许列表，不接受 AI 或用户输入拼接成任意 shell 命令。

每个命令定义：

```text
命令模板
允许参数
是否需要 sudo
最大执行时间
最大输出大小
支持的发行版
失败处理方式
```

禁止命令包括但不限于：

* 修改文件或权限的命令。
* 启停和重启服务的命令。
* 软件安装、升级和删除命令。
* 磁盘挂载、格式化和分区命令。
* 网络、防火墙和用户修改命令。

### 8.4 审计

每次扫描保存：

* 操作者和目标主机标识。
* 扫描开始、结束时间。
* OpSense 和规则版本。
* 实际执行的命令及退出状态。
* 权限提升记录。
* 脱敏计数和规则版本。
* AI Provider、thread ID 和分析状态。

## 9. 报告设计

第一版以 Word（`.docx`）作为默认最终报告格式。报告层直接根据结构化快照和 AI 分析结果生成 Office Open XML 文档，不依赖 Pandoc、LibreOffice 或 Microsoft Word 参与转换。

### 9.1 输出目录

```text
report/<host>/<scan-time>/
|-- README.md
|-- 服务器巡检报告-<服务器标识>-<YYYY-MM-DD_HH-mm-ss>.docx
|-- system.md
|-- storage.md
|-- network.md
|-- services.md
|-- services/
|   |-- nginx.md
|   |-- order-api.md
|   `-- postgresql.md
|-- findings.md
|-- unknowns.md
|-- snapshot.json
`-- index.html
```

其中 `服务器巡检报告-<服务器标识>-<YYYY-MM-DD_HH-mm-ss>.docx` 是正式交付文件；`index.html` 是必须生成的离线浏览报告；Markdown 文件用于调试、审阅和内容追溯。Word 与 HTML 必须由同一份 `ReportModel` 渲染，确保章节、事实数据、风险和未知项一致。

HTML 报告必须能够通过文件系统直接打开，不依赖本地 HTTP 服务或外部 CDN。样式、脚本和必要资源应内联或输出到同一报告目录，所有来自快照和 AI 的文本必须经过 HTML 转义，并继续遵循 M7 脱敏边界。

Word 文件名采用以下规则：

```text
服务器巡检报告-{服务器标识}-{YYYY-MM-DD_HH-mm-ss}.docx
```

服务器标识直接取本次扫描目标：目标为 IP 时使用 IP，目标为 DNS 名、主机名或服务名时使用对应名称。示例：

```text
服务器巡检报告-192.168.168.12-2026-08-14_16-36-12.docx
服务器巡检报告-prod-web-01-2026-08-14_16-36-12.docx
```

文件名生成器必须移除控制字符，将 Windows 非法字符 `< > : " / \\ | ? *` 替换为 `_`，去除结尾空格和句点，并限制服务器标识与最终文件名长度。IPv6 地址保留地址信息，但将冒号替换为下划线。扫描时间默认转换为报告生成机器的本地时区，使用常见且文件名安全的 `YYYY-MM-DD_HH-mm-ss` 格式，例如 `2026-08-14_16-36-12`；时分秒使用连字符代替 Windows 文件名不允许的冒号。时间字段保证同一服务器多次生成报告时不会互相覆盖，文档正文同时保留带时区的完整时间。若清理后的服务器标识为空，则回退为 `未知服务器`。

### 9.2 Word 文档结构与样式

Word 报告至少包含：

1. 封面：主机标识、扫描时间、OpSense 版本和报告状态。
2. 自动目录：使用 Word 标题级别生成，可在打开文档后更新域。
3. 执行摘要：服务器用途、资源概况、服务数量和重点风险。
4. 系统环境：操作系统、CPU、内存、网络和权限概况。
5. 磁盘与目录：磁盘、分区、挂载点、使用率和主要目录表格。
6. 部署服务清单：服务状态、部署方式、端口和路径汇总表。
7. 服务详情：每个服务的配置、日志、数据和启动信息。
8. 风险与待确认项。
9. 证据附录：重要结论对应的 evidence ID 和来源。

样式要求：

* 使用 Heading 1/2/3 标题层级，不手工模拟标题样式。
* 表格在页面宽度内自适应，长路径允许换行。
* 命令和路径使用等宽字体。
* 页眉显示主机名，页脚显示生成时间和页码。
* 服务详情之间使用分页控制，避免标题单独出现在页尾。
* 中文正文使用常见中文字体，并设置可替代字体。
* 文档应能在 Microsoft Word 和 WPS 中打开，不出现修复提示。

### 9.3 基础报告与 AI 报告

* 基础报告完全由结构化快照生成，保证无 AI 时仍可使用。
* 无 AI 时由基线分类器保守区分部署服务、系统服务和待确认候选。
* AI 内容使用明确标识，显示确定程度和证据引用。
* AI 调用失败不影响快照和基础报告产出。
* 用户可以选择重新运行 AI 分析，而不重新扫描服务器。
* 重新运行离线 AI 分析可以更新分类和报告投影，但不能执行需要 SSH 的补探测。

### 9.4 服务页面

报告服务部分按以下层级组织：

* 主要部署服务：业务应用和主要运行组件。
* 支撑组件：数据库、中间件、代理、容器平台和存储组件。
* 系统服务概况：统计普通 Linux systemd 服务，只展开失败、外部监听或与部署直接相关的异常项。
* 待确认服务：证据不足或分类冲突的候选。
* 完整候选索引：保留所有服务 ID、分类和 Evidence，避免降噪造成事实丢失。

主要部署服务、支撑组件和待确认服务页面至少显示：

* 名称、状态和部署类型。
* 进程、端口和启动时间。
* 部署目录、配置、日志和数据位置。
* systemd 或 Docker 启动信息。
* 开机自启动和容器重启策略。
* AI 生成的用途说明。
* 确定事实、合理推断和未知项。
* 对应证据和采集时间。

## 10. 本地 CLI 草案

```bash
# 扫描并生成基础快照
opsense scan --host server.example.com --user ops

# 使用已有快照进行离线 Codex 分类和分析；只生成补探测计划，不重新连接服务器
opsense analyze --scan <scan-id> --provider codex

# 生成报告
opsense report --scan <scan-id> --format docx

# 一次完成扫描、AI 分析和报告生成
opsense inspect --host server.example.com --provider codex

```

第一版允许在可信内网环境通过 `--password` 传入明文 SSH 密码，但密码只允许保存在当前进程内存中，不得写入配置文件、审计日志、扫描快照、AI 输入或报告。仍优先推荐 SSH Agent 和密钥文件；命令行密码可能暴露在 Shell 历史和进程列表中。

独立 `analyze` 命令不持有 SSH 凭据，只对现有脱敏快照进行分类、生成 `ProbeRequest` 和最终分析。只有 `inspect` 在认证信息仍位于当前进程内存、SSH 会话可复用或可安全重连时，才允许执行一轮通过 `ProbePlanValidator` 的补探测。OpSense 不得为了离线分析保存密码或私钥副本。

第一版的主流程可以简化为：

```bash
opsense inspect --host server.example.com --user ops --provider codex
```

执行完成后，CLI 直接输出本地报告目录。用户不需要启动服务或打开管理后台。

### 10.1 执行阶段

```text
created
connecting
collecting
normalizing
redacting
planning
enriching
analyzing
rendering
completed
partial
failed
```

`partial` 表示部分采集步骤因权限或命令缺失失败，但已有结果仍可使用。

### 10.2 本地配置

默认配置文件为 `~/.opsense/config.json`：

```json
{
  "ssh": {
    "connectTimeoutMs": 10000,
    "commandTimeoutMs": 30000,
    "strictHostKeyChecking": true
  },
  "scan": {
    "maxDirectoryDepth": 4,
    "maxFilesPerDirectory": 5000,
    "maxConfigFileBytes": 262144,
    "crossFileSystems": false,
    "useSudo": "auto"
  },
  "ai": {
    "enabled": true,
    "provider": "codex",
    "maxRetries": 2,
    "enableProbeEnrichment": true,
    "maxProbeRequests": 20,
    "maxProbeDepth": 2,
    "maxProbeMatches": 100,
    "maxProbeTotalBytes": 5242880
  },
  "report": {
    "formats": ["docx", "html"]
  }
}
```

SSH 私钥路径可以通过主机配置或命令行参数指定，但密码和私钥正文不得写入 OpSense 配置文件。命令行参数优先级高于本地配置。

## 12. 测试与验收

### 12.1 测试层次

* 单元测试：命令解析、配置解析、脱敏和服务归并。
* Golden 测试：固定命令输出对应固定结构化结果。
* 镜像测试：在多个 Linux Docker 镜像中验证基础采集。
* 虚拟机测试：验证 systemd、磁盘、挂载和权限行为。
* 场景测试：传统应用、Docker Compose、Nginx、数据库组合。
* AI 契约测试：验证 JSON Schema、证据引用和禁止猜测规则。
* 安全测试：确保 fixture 中注入的 Token、密码和私钥不会进入 AI 输入。

### 12.2 第一阶段验收标准

1. 支持 Ubuntu 22.04/24.04、Debian 12、Rocky Linux 9。
2. 普通用户权限下可以生成部分可用报告。
3. 特权只读模式能识别系统、磁盘、挂载、进程、端口和 systemd。
4. 能识别正在运行和已停止的 Docker 容器及 Compose 项目。
5. 能把 systemd、PID、端口和部署目录归并到同一服务。
6. 不执行任何修改服务器状态的命令。
7. 测试密钥、密码和 Token 不进入 Codex 输入目录。
8. Codex 不可用时仍能完成扫描并生成基础报告。
9. AI 结论包含确定程度，重要结论可以追溯到 evidence ID。
10. 扫描失败项、权限不足项和未知项在报告中明确展示。
11. 可以生成有效的 `.docx` 文件，并能在 Microsoft Word 和 WPS 中正常打开。
12. Word 报告包含封面、目录、标题层级、表格、页眉页脚和证据附录。

## 13. 实施计划

### 阶段 0：数据契约和项目骨架

* 建立 TypeScript workspace 和本地 CLI。
* 定义 ScanSession、Host、Storage、Process、Socket、Service 和 Evidence Schema。
* 定义 SSH 命令允许列表和统一执行结果。
* 建立 fixture 和 Golden 测试机制。

交付物：可以读取 fixture 并生成空框架报告。

### 阶段 1：系统与存储采集

* SSH 连接、命令模板编排和超时控制。
* OS、CPU、内存、磁盘、分区、挂载、空间和网络采集。
* 发行版识别、逻辑探针、命令变体降级和跨版本解析。
* 命令超时、输出限制、权限状态和审计日志。

交付物：`opsense scan` 生成主机基础快照。

### 阶段 2：服务探测

* systemd、进程、端口采集。
* Docker、Compose、Volume 和 Mount 采集。
* Nginx、Caddy 和常见数据库入口探测。
* 路径种子和受限目录扫描。

交付物：生成初步部署服务清单。

### 阶段 3：归一化和报告

* 服务归并和证据索引。
* 确定程度与未知项处理。
* Word（`.docx`）和静态 HTML 报告，以及用于调试的 Markdown 文件。

交付物：不使用 AI 也可以生成可读服务器文档。

### 阶段 4：Codex 接入

* 实现 `AiProvider` 和 `CodexProvider`。
* 实现基线服务相关性分类器和报告投影。
* 生成脱敏的紧凑 Codex 候选工作区。
* 定义服务分类、路径分类、ProbeRequest 和最终分析 Schema。
* 编写分类阶段与最终分析阶段提示词。
* 实现 ProbePlanValidator 和一轮受控补探测接口。
* 增加 JSON 校验、重试、超时和 thread ID 保存。
* 在报告中显示主要服务、支撑组件、系统服务概况、待确认候选和完整索引。
* 建立跨发行版系统服务降噪与非标准服务识别评测集。

交付物：`opsense analyze --provider codex` 完成离线分类；`opsense inspect --provider codex` 可执行受控补探测闭环。

### 阶段 5：本地工具质量完善

* 多发行版虚拟机测试。
* 扫描性能、断点和增量扫描。
* 更完整的敏感信息规则。
* 本地安装包、版本升级和错误诊断。
* Word 报告模板、样式和本地浏览体验优化。
* 可选的历史快照索引和差异比较。

## 14. 主要风险与应对

| 风险 | 应对措施 |
| --- | --- |
| 权限不足导致信息缺失 | 支持部分结果，明确记录权限缺口，不强制要求 root |
| 全盘扫描耗时过长 | 运行态线索驱动、限制深度和文件数、默认不跨挂载点 |
| 配置中存在密钥 | 远程命令只提取必要字段，本地落盘前脱敏，敏感值不进入快照和 AI |
| AI 生成无证据结论 | 结构化输入输出、evidence ID、Schema 校验和报告分层 |
| 服务重复识别 | 使用 PID、cgroup、unit、容器 ID 和路径进行确定性归并 |
| 不同发行版命令不一致 | 命令 capability 探测和发行版适配层 |
| Codex 不可用 | NoopProvider 和基础报告始终可用 |
| SDK 或模型能力变化 | Provider 隔离、锁定依赖版本、集成测试验证 |

## 15. 关键设计结论

1. 不先扫描完整目录树，先从系统、进程、systemd、端口和容器获得路径线索。
2. 本地 CLI 只通过 SSH 执行允许列表中的只读命令，不在目标服务器安装 Agent。
3. 原始事实、规则推断和 AI 解释分层保存。
4. 第一阶段使用本地 JSON 文件和目录，不引入数据库。
5. 第一版统一使用 TypeScript，本地 CLI 负责 SSH 采集、归并、报告和 Codex SDK 接入。
6. Codex 是首选 AI Provider，但不是扫描和基础文档生成的必要条件。
7. 安全和脱敏必须在 AI 调用之前完成，远程采集应避免输出不必要的敏感值。
8. 第一版是纯本地工具，不包含 Web 管理系统、中心服务和任务队列。
9. Word（`.docx`）是第一版默认正式交付格式，静态 HTML 是必须生成的离线浏览格式，Markdown 作为辅助输出。
